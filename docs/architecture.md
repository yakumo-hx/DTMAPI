# DTMAPI 架构

DTMAPI 让 Mod 能在《多洛可小镇》里运行。BepInEx 把 DTMAPI 带进游戏；DTMAPI 从游戏官方的 MODS 目录和创意工坊订阅里找到 Mod，按官方的启用状态加载它们，给它们一套稳定的 API，并在 Mod 出错时把它和其他 Mod 隔开。

本文写的是目标结构。代码还没完全到位的地方，列在最后一节"还没做到的"里，做完一项删一项。

## 交付什么

| 交付物 | 给谁 | 里面有什么 |
| --- | --- | --- |
| Runtime | 玩家 | BepInEx，DTMAPI 运行时 DLL，三个内置内容模块（畜牧、怪物、音频） |
| Mod | 玩家 | 放在官方 MODS 目录或创意工坊里的 CodeMod 或内容包 |
| 作者工具 | Mod 作者 | 用来编译的 API 引用 DLL，命令行工具（新建、打包、部署、检查），原生引用生成器，音频准备工具 |
| 安装器 | 玩家 | 安装、卸载、状态检查、收集日志 |

## Mod 的三种形式

| 形式 | 是什么 |
| --- | --- |
| CodeMod | 普通的 `netstandard2.0` DLL。入口类继承 `DtmMod`，在 `Entry(IDtmHelper)` 里初始化。可以引用 DTMAPI 公共 API 和游戏程序集。 |
| 内容包 | 不含代码的目录。游戏原生格式的内容放 `Content/`；DTMAPI 扩展的内容（新动物、怪物、声音）放 `PackData/content.json`。 |
| 外部 BepInEx 插件 | 直接放进 `BepInEx/plugins` 的第三方插件。DTMAPI 只在诊断里把它列出来，不管理它。 |

Mod 放在游戏官方的本地 MODS 目录或创意工坊订阅里。历史上的 `<游戏目录>/Mods` 不再参与查找。`BepInEx/plugins/DTMAPI` 只放 DTMAPI 自己的文件。包的目录结构见作者文档。

## 运行时分层

```text
编译引用（A ──> B 表示 A 引用 B）

  Bootstrap ──> GameBridge ──> Core ──> Abstractions
  Bootstrap ──> ModConfigMenu ──> Abstractions
  Modules.Animals / Monsters / Audio ──> RuntimeModules ──> 内容契约 ──> Abstractions
  Mod ──> Abstractions、ModConfigMenu、内容契约、游戏程序集

运行时按需加载（不是编译引用）

  Core ┄┄> RuntimeModules ┄┄> Modules.*
```

图里没画的辅助库（比如 AudioPreparation），算作使用它的那一层。规则只有五条：

1. 依赖只能顺着箭头走，不能反过来。
2. Abstractions、ModConfigMenu、内容契约、Core、RuntimeModules 不引用游戏、Unity、Harmony 或 BepInEx 的类型，所以都能离线测试。
3. 接触游戏类型的只有 GameBridge、Modules.*、Bootstrap 和 Mod。
4. 平台代码（Mod 以外的所有部分）里不出现任何具体 Mod 的名字。
5. `InternalsVisibleTo` 不能给 Mod，也不能给 QA。

## 各部分负责什么

| 程序集 | 负责 | 不放这里 |
| --- | --- | --- |
| `DTMAPI.Abstractions` | 作者 API：`DtmMod`、`IDtmHelper`、事件、配置、输入、日志、命令、数据文件、翻译 | 实现代码，只给某个 Mod 用的协调器，诊断用的数据结构 |
| `DTMAPI.ModConfigMenu` | 配置菜单的 API 和页面模型 | 游戏界面的绘制 |
| 内容契约：`DTMAPI.AudioContent`、`AnimalContent`、`MonsterContent` | 内容定义的类型，以及读取 `content.json` 的代码 | 游戏类型，编辑器专用的逻辑 |
| `DTMAPI.Core` | 找 Mod、排依赖顺序、加载、Mod 注册内容的登记和收回、各项服务的实现、出错隔离、日志、管理页的数据 | 游戏类型，Harmony，官方内容的第二份索引，运行时 IPC，观察账本 |
| `DTMAPI.GameBridge.DolocTown` | 把游戏事件转成 DTMAPI 事件（读档、保存、回标题、每帧、菜单、输入、创意工坊订阅）；简单的原生查询；至少两个 Mod 共用的游戏接点；Harmony 补丁的安装，以及撤销 Mod 的补丁 | 只为一个 Mod 服务的逻辑，QA 入口，旧接口的兼容宿主 |
| `DTMAPI.RuntimeModules` | 内置内容模块的托管部分：合并内容，提供作者 API，管理每个 Mod 贡献的内容 | 游戏类型 |
| `DTMAPI.Modules.Animals` / `Monsters` / `Audio` | 内置内容模块的游戏部分：Hook、创建实例、加载资源、释放资源。没有内容用到时不启动。 | 别的模块的逻辑 |
| `DTMAPI.BepInExBootstrap` | BepInEx 插件入口：把各部分组装起来，驱动每帧更新，提供标题页的设置入口 | QA 加载器 |

作者工具和安装器是普通的 .NET 8 程序，可以引用内容契约来读写同一种格式。运行时不引用工具。

## 主要流程

### 启动

1. BepInEx 加载 Bootstrap。
2. Bootstrap 创建 Core 和 GameBridge，装上平台每次都要用的 Hook（每帧、读档、保存、回标题）。其他 Hook 等第一次有人需要时再装。
3. GameBridge 拿到官方的订阅快照。Core 从官方本地 MODS 目录和订阅里列出 Mod，按官方的启用状态和顺序筛选。同一个 Mod 本地和创意工坊各有一份时，加载哪一份由来源选择决定（`AuthorSourceState.cs`），它是加载的一部分。
4. Core 按依赖顺序加载每个 Mod：读 manifest，加载程序集，调用 `Entry`。内容包的 `PackData/content.json` 交给对应的内置模块处理。内置模块要等有内容用到它时才启动。
5. 某个 Mod 加载失败时，报告原因，跳过它和依赖它的 Mod，其他 Mod 照常加载。

### 玩家在官方页面改了 Mod 列表

官方 Mod 页面只能从标题页打开。玩家关闭页面且官方保存成功后，DTMAPI 按依赖顺序加载新增包，跟启动时调用同一个单包入口。依赖按本次已经加载的版本和已经绑定的程序集判断。之前缺少依赖的包，依赖可用后一起加载。

每个包只初始化一次，包括 `PackData/content.json`。晚加载的包追加内容顺序，加载完成后更新包资源查询、内容清单和配置页锁。`GameLaunched` 只补发给这次新增的 Mod；随后发出 `ModListChanged`。

已经运行的包保持原实例。取消勾选，显示“重启后停用”；重启前勾回原包，取消待停用提示。更换版本或来源，重启后生效。作者声明 `RequiresRestart`，或者必需依赖正在等待新版本，也显示重启原因。加载失败显示具体原因，不影响其他包；进入初始化后失败，本次不重试。

关闭页面后，需要重启时弹出“需要重启”，只列 Mod 名称。加载失败也弹出名称和原因，两类情况合并为一个框；加载成功不弹。管理页按包显示本次实际状态：运行中、重启后停用、重启后生效及原因、加载失败及原因。

### Mod 注册的东西怎么收回

Mod 通过 helper 注册的东西（事件、输入、命令、配置页、内容），以及 Mod 自己用 Harmony 打的补丁（按补丁方法所在的程序集认），都记在这个 Mod 名下。下面两种情况会收回：

- `Entry` 抛出异常：收回它已经注册的全部内容。
- Mod 自己释放注册时拿到的句柄：只收回这一项。

Entry 失败时先调用 Mod 的清理，再从依赖加载器读取绑定关系。只收回独占程序集里的 Harmony 补丁；共享程序集的补丁保留，报告清理未完成、需要重启。绑定关系只存一份，不向 Harmony 服务复制。退出进程时不额外收回 Harmony 补丁，也不等待仍在加载的后台线程。

其他注册按注册的相反顺序收回。程序集一旦加载就卸不掉，所以代码要等重启后才算真正移除。这是正常情况，不是错误。

### 存档

只有游戏的原生保存成功，进度才算保存了。睡觉、存档菜单这些入口会调用原生保存；回标题、不保存就退出、游戏崩溃，都会丢掉上次保存之后的变化。跨日、昏倒、关掉界面、时间流逝，这些都不等于保存；要以原生保存的结果为准。

Mod 的玩法数据（物品、装备、耐久、经济、任务、世界状态）跟着原生存档走：

1. 读档时，读入上次保存的数据。
2. 游玩过程中的变化只放在内存里。
3. 原生保存时一起写入。推荐写进原生存档自带的变量存储，这样它和原生存档同时落盘，不需要另外的文件，也不需要恢复流程。MoreEquipmentSlots 就是这样做的。
4. 没有原生保存就离开，内存里的变化直接丢掉，跟游戏本身的行为一致。

如果一定要用单独的文件：在保存事件里先写临时文件，确认原生保存成功后，再替换正式文件。

配置、按键、日志不属于玩法数据，可以随时写盘。想偏离这条规则，需要用户做出产品决定，并告知玩家。

### 出错时

只在下面四个边界捕获异常：

1. **调用 Mod 代码时**（`Entry`、事件回调、命令、配置回调、模块回调）：捕获异常，记到这个 Mod 名下，其他 Mod 照常运行。
2. **平台自己的 Hook 回调里**：捕获异常，记日志，游戏原来的逻辑照常执行。
3. **每帧更新时**：捕获异常，记日志。
4. **读文件、找游戏成员时**：失败就报告具体是哪个文件、哪个成员，跳过这一项，其余照常。

其他地方都不捕获。错误只出现在两个地方：日志文件，以及管理页上的 Mod 状态。

## 线程、每帧更新和事件

### 线程

运行时只在 Unity 主线程上跑。公开 API 本来就要求在主线程调用，平台内部也按这个写：主线程上的状态不加锁。

能从别的线程进来的只有四处（11-07 用户批准 CLR 加载依赖例外）：

| 入口 | 做法 |
| --- | --- |
| 调度器提交（`IDtmScheduler`） | 放进一个加锁的队列，到主线程上再执行 |
| 日志 | 写文件时加锁 |
| CLR 加载依赖程序集（`AssemblyResolve`、`AssemblyLoad`） | 在请求线程上同步解析。加载器自己的候选表、绑定表用一把短锁；锁不包住 `Assembly.LoadFrom`、平台回调和 Mod 代码。回调不改平台其他状态。要用绑定关系时，由主线程当时复制一份 |
| 运行时上下文快照（`IDtmRuntimeContext.Snapshot`） | 主线程生成新的快照对象，整个替换引用；读的一方不加锁 |

后台任务（比如音频缓存的解码）只碰自己的数据。结果由主线程来取：轮询任务是否完成，或者经调度器交回主线程。平台状态、事件和 Mod 代码只在主线程上碰。

### 每帧更新

每帧只更新一次，入口有两个：

- 游戏内：原生 `NormalGameState.OnUpdate` 的 Hook。
- 其他时候（标题页、读档过程中）：Bootstrap 装进 Unity PlayerLoop 的回调。读档、回标题、读档返回以后，各重新装一次。

两个入口调用同一个更新方法。PlayerLoop 回调先看帧号：上一帧原生入口触发过，这一帧就不跑。同一帧只更新一次，按键也只在这时读一次。不用时间窗。

### 事件和 Hook

- 事件在主线程上同步发出：拿订阅列表的一份副本，逐个调用。回调里新增或取消的订阅，从下一次事件开始生效。
- 每个回调都是"调用 Mod 代码"的边界：出错记到这个 Mod 名下，接着调用下一个。
- 事件不排队，也不合并。
- 平台每次都要用的 Hook（每帧、读档、保存、回标题）在启动时安装。其他 Hook 等第一次有人需要时（订阅了对应的事件，或者注册了对应的内容）再装，装上就不卸载。没人用的时候，Hook 直接放行游戏原来的逻辑。这里说的只是平台自己的补丁；Mod 打的补丁见"Mod 注册的东西怎么收回"。
- Hook 装不上（找不到游戏成员）：报告是哪个成员，依赖它的功能不可用，其他照常。

## 游戏相关的代码放在哪

| 代码 | 放哪 |
| --- | --- |
| Mod 加载、配置、日志、命令、数据目录、管理页 | 平台：Core、Abstractions、Bootstrap、ModConfigMenu |
| 至少两个真实 Mod 都要用的同一个游戏接点 | GameBridge |
| 只有一个 Mod 用的补丁、状态、缓存、界面、玩法 | 这个 Mod 自己 |
| 内容格式、读取、校验、按内容创建游戏对象 | 内置内容模块 |
| 具体的内容（一种动物、一首歌） | 内容包 |

"以后可能会复用"、"测试里有第二个用户"，都不算两个真实 Mod。

能交给游戏自己做的事，就交给游戏：官方表的加载与合并、同 ID 覆盖、本地化、资源查找、内容优先级、上传判定，都归游戏。DTMAPI 只读取结果，只补游戏没有的部分。

Harmony 只在 GameBridge、`Modules.*` 和 Mod 里用。GameBridge 编译期引用 HarmonyX 2.9.0 的 NuGet 包，只用来编译，不随包分发；运行时用的是 BepInEx 自带的那一份，版本相同。撤销 Mod 的补丁也由 GameBridge 来做。Core 不碰 Harmony，也不通过反射去碰。

## 公共 API

- 公开的程序集有五个：Abstractions、ModConfigMenu、AudioContent、AnimalContent、MonsterContent。程序集名不改。
- API 只有两个级别：**Stable**，承诺兼容；**Experimental**，可能会变，变的时候写进 CHANGELOG。
- 破坏性变化只在明确的破坏性版本里做（比如 0.7.5），同时写进 CHANGELOG 和迁移说明。改动不能让支持范围以内、现在能加载的 Mod 加载失败，见下一节。
- 旧版本的源码不存进仓库，需要时看 git tag。
- API 只暴露 DTMAPI 自己的类型，不暴露 Unity、Harmony、BepInEx 或游戏的类型。
- 版本号：Runtime 只有一个版本号，内置模块跟着它走。Mod 在 manifest 里写自己需要的最低 Runtime 版本。

## 兼容已发布的 Mod

- 支持范围：0.6.0 及以后的 API target。0.6.0 之前的 API target、旧 Mod 和旧构建不再维护，见作者文档 `API-STATUS.md`。保留下来的旧类型，以及程序集版本号 0.5.3.0，都不扩大这个范围。
- 已经退役的旧类型不恢复，也不留转发壳。
- 范围以内的改动，不能让现在能加载的 Mod 加载失败。删改公开 API 之前，先查创意工坊上实际的引用。查出问题，改这次的改动；已经批准退役的接口还有人在用，先问用户。
- 重构 manifest 读取时，现在能读的写法保持能读。
- 不加拒载名单，也不为个别 Mod 写兼容代码。

## 不做的事

| 不做 | 原因 |
| --- | --- |
| 准入等级、生成证明、SDK 注册 | Mod 就是普通 DLL，加载时看它实际的依赖。 |
| 运行中停用、卸载、换掉 Mod 的代码 | Mono 卸不掉程序集。取消勾选和换版本，重启后生效。同一个 Mod 一次运行里只加载一次。 |
| 维护官方内容的第二份索引或缓存 | 表、资源、优先级、本地化都归游戏，DTMAPI 读结果就行。 |
| 替不在场的 Mod 保管或恢复数据 | 数据在原生存档里，Mod 回来时自己读。 |
| 运行时 IPC、作者会话 | 开发时看日志、重启游戏就够了。 |
| 常驻的性能采样、对象图快照、观察账本 | 需要时用 QA 工具临时测量。 |
| 按测试样本定平台上限 | 上限只来自技术约束。 |
| 为没发布、或者没人用的旧接口保留兼容宿主 | 兼容只给已发布、而且确实有人在用的接口。 |
| 多线程访问平台状态，给主线程上的状态加锁 | 公开 API 只在主线程调用。跨线程的只有调度器、日志、上下文快照、CLR 加载依赖四处。 |
| 多个每帧来源互相仲裁，按时间窗切换 | 游戏内用原生更新，其他时候用 PlayerLoop，按帧号判断就够了。 |
| 事件排队、合并、投递收据 | 事件都在主线程上同步发出。 |
| 卸载平台自己的 Hook | 没人用时，Hook 只多一次判断。装上就留着，省掉一整套装卸状态。Entry 失败时只收回该 Mod 独占程序集中的补丁。 |
| 维护 0.6.0 之前的 API target | 已经停止。旧类型在 0.7.5 删除，不恢复。 |
| 通过反射调用 Harmony | GameBridge 编译期引用 HarmonyX，跟 BepInEx 自带的版本一致。 |

## 架构检查

`tests/DTMAPI.Architecture.Tests` 里有三项检查，这是仅有的读源码的测试：

1. 引用符合上面的分层图：运行时工程只引用图里允许的工程；规则 2 里的工程不引用游戏、Unity、Harmony 或 BepInEx；Mod 只引用五个公开程序集；`InternalsVisibleTo` 不给 Mod，也不给 QA。
2. 平台工程的源码里不出现第一方 Mod 的 UniqueID 或名字。
3. 代码和文件名里没有阶段号、批次号、轮次号。

旧代码里已有的问题，记在同一目录的 `known-violations.txt` 里。这份清单只能删，不能加：出现新问题，测试失败，要改代码；清单里的问题修好了，测试也会失败，提醒你把那一行删掉。

## 构建

- `DTMAPI.sln` 包含平台、作者工具和离线测试。内置游戏模块和第一方 Mod 分别用 `build-runtime-modules.ps1`、`build-mod-project.ps1` 构建。`Modules.*` 和 `mods/` 要引用游戏程序集，所以只能在装了游戏的机器上构建：先用原生引用生成器，从本机游戏生成编译用的引用，再构建。
