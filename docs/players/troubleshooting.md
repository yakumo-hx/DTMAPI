# 玩家反馈与故障排查

| 类型 | 首先收集 | 执行路线 |
| --- | --- | --- |
| 操作或预期差异 | 预期、操作步骤、设置 | 解释或修正文档；确需改行为才进入产品实施 |
| Mod 缺陷 | 实际加载来源/版本、最小复现、相关日志 | 对应产品、既有问题和具体复现场景 |
| 安装环境 | 失败阶段、路径、安装器输出 | 按所用发行包的安装说明排查 |
| 游戏本体问题 | 游戏 build、原生表现、Mod 是否介入 | 匹配原生事实和版本差异，不先归因 Mod |
| 存档损坏 | 原件、槽、已知进度和明确修复范围 | 离线分析、派生修复、允许差异验证、交付读档 |

## 工坊订阅后找不到安装包目录

先从 Steam 库中多洛可小镇的“属性 → 已安装文件 → 浏览”定位实际游戏目录，返回同一座库的 `steamapps`，检查 `workshop/content/2285550`。Windows DTMAPI 安装包在其下的 `3743016467`，多平台包在 `3792681186`；截图只有其他游戏的数字目录时，不能据此认定 DTMAPI 安装器失败。

**确认路径无误且已订阅，仍找不到对应工坊目录时，优先建议退出游戏，取消订阅该 DTMAPI 条目后重新订阅，等待该游戏的工坊内容下载完成，再刷新目录。** 不要求玩家手动新建空目录，也不需要为此退订全部功能 Mod。

恢复后可按玩家确认关闭，明确保留“根因未确认”；重新订阅有效不证明某个具体 Steam 内部故障。若仍未恢复，再收集 Steam 客户端 `logs/workshop_log.txt`、`logs/content_log.txt` 和目标库的 `steamapps/workshop/appworkshop_2285550.acf`（不存在就记录缺失），区分订阅识别、下载调度与文件落盘阶段。

## 先分流，再取证

使用 Runtime 安装包中的“收集日志”入口。记录实际安装位置、Runtime 和 Mod 版本、预期与实际表现，并区分“观察”和“推断”。日志已能定位的问题不需要提供存档；只有存档相关案件才采集明确需要的槽位。

先关闭游戏，再采集一次稳定快照。提交前确认采集范围，保留原件，不把指定槽采集写成完整 SAVE 取证。真实修档应从原件派生到新目录，不直接覆盖提交的原件。普通功能测试不因此增加例行原生保存或存档改写。

## 存档问题的验证边界

离线分析、格式兼容、成功读档和具体任务结果是不同结论。恢复包若绑定旧原件，而玩家此后主动保存产生了新文件，就应重新采集并判断，不能只改旧记录中的哈希。

修复只针对明确授权、已经识别的故障范围；格式不明、前提不完整或存在冲突时应停止，不自动扩大修复。不得修改槽号来伪装成另一槽。内部格式材料、原始支持包和分析材料不随修复结果公开分发。

需要真实游戏验收时，应使用明确授权的派生件，检查命名的任务或 UI 结果及相关日志。成功加载仅证明格式和读档兼容；原生接受任务等行为未验证时必须单独写明。合成测试不能代替玩家可用证明，未收到玩家确认不能写成“玩家已解决”。
