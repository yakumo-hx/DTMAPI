# 其他开发者支持计划：公开源码交付与有限 Linux 构建测试

- Lifecycle: `proposed`；本次完成设计，尚未实施。
- 基线：已通过验收的 0.7.0，Runtime r6、多平台 r2、Author SDK D7。
- 适用事项：用户编号 2「远端源码交付重构」和编号 3「0.7.1 的贡献者构建、通用测试及必要脚本拆分」。
- 不包含：编号 1 的 Steam 上传；本次不推送、合并、移动标签、修改产品代码或重跑游戏验收。
- 计划位置：独立的“其他开发者支持计划”，不调整 [platform-next 主线](platform-next/README.md)的 API、内容能力、版本验收任务或优先级。
- 本次记录：[20260911-0002](../updates/2026/20260911-0002-contributor-support-plan.md)。

## 1. 采用的方案

以一份源代码、一套 MSBuild 工程关系、一套测试分类为基础，提供两种开发入口：Windows 保持正式开发与发布能力；Linux 贡献者可以编译声明范围内的源码、运行不依赖游戏的通用测试。Linux 能力安排在 0.7.1 的独立工作线上，不阻塞 0.7.0 源码交付，也不自动成为 Windows 产品发布门禁。

公开仓库由固定的内容边界从准确源码提交生成，日后通过普通 PR 持续更新。公开目录尽量与内部同路径，贡献者 PR 可以按正常 Git 流程回流；不按每个版本重新挑文件，也不维护一套翻译成 Bash 的构建、安装和游戏测试脚本。

这项设计可以减少重复维护，但不能承诺“实现一次，以后零维护”。新增测试仍要声明范围，新增公开依赖仍要核对交付条件，真实的跨平台缺陷仍要处理。目标是把这些工作并入普通变更审查，不增加每版一次的专项迁移工程。

### 支持边界

| 能力 | 本计划承诺 | 验证与限制 |
| --- | --- | --- |
| Windows 开发 DTMAPI、现有完整 SDK、正式打包及真实游戏验证 | 保留现有正式流程 | 继续按既有产品与发布规则验证 |
| 公开仓库的 Windows 源码构建和公开测试 | 必须具备 | 干净克隆，只使用公开材料；不要求取得内部工作区 |
| Linux 编辑、IDE、声明范围内的源码构建 | 有限支持，按最佳努力维护 | 首轮用一套 WSL2 Linux 环境验证；准确列出项目和前提 |
| Linux 通用测试 | 与 Windows 共用实现 | 被选中的测试必须真实通过；不能用批量 skip 制造通过 |
| Linux 完整解决方案、完整 Author SDK 作者流程、正式封包/发布 | 不新增承诺 | 可移植的局部 SDK 测试可以纳入通用范围，不由此承诺整个流程 |
| Linux 的 Windows 游戏注入、Steam/Proton、HookProbe 和真实存档测试 | 不纳入本计划 | 它们验证游戏宿主，不能由纯源码测试或 WSL 假目录替代 |
| 已存在的多平台玩家包、Linux 安装器及其测试 | 保留现有边界 | 本计划不撤销这些交付，也不以此宣称 Steam Deck 实机通过 |
| Linux CI | 首轮可不建设；有需要时增加一个手动、非必需任务 | 复用同一测试入口；不新增独立发布流程或常驻服务 |

面向贡献者的说明必须同时列出“能做什么”和“没有验证什么”。`best effort` 表示平台维护优先级有限，不表示把已执行失败的断言改成通过，也不表示所有带有 Linux 字样的 PR 都应接受。

## 2. 当前事实与外部反馈

### 2.1 0.7.0 已有的基础

最新 [SDK 首次交付记录](../updates/2026/20260910-0012-sdk-msbuild-first-release.md)确认 D7、r6、r2 已完成具名验收。当前 [候选交付表](platform-next/release-candidate.md)负责准确包身份，本计划不另维护一张包版本表。技术验收与实际上传分开记录。

当前工作区仍有未提交的 0.7.0 源码和文档变更。此次读取时 HEAD 为 `cc7044a7`，它不能直接代表全部已验收 SDK 源码。首次公开交付需要把被选择的准确源码纳入一个明确的提交，并与已有输入摘要对应；不能拿“当前 HEAD”标注一个实际上从脏工作树复制出来的导出包。

对 0.6.1 的批评应逐项核对，不能整体套用到 0.7.0：

| 说法 | 当前仓库的观察 | 本计划的处理 |
| --- | --- | --- |
| `build.ps1` 自己维护编译工程图 | 当前入口约 41 行，调用一次 `dotnet build DTMAPI.sln`；SDK 也已转标准 MSBuild | 保持这一方向，不再另造构建系统；测试集合与编译依赖仍需区分 |
| `run-game-smoke.ps1` 是一万多行单文件 | 当前入口约 280 行，已拆成 22 个模块；模块合计仍较大 | 不重新整批拆分或 Linux 化；只有后续实际修改触及的模块才做局部整理 |
| 通用测试被 Windows 环境限制 | `test-public-source.ps1` 显式要求 Windows/Windows PowerShell 5.1，且混入多种维护者测试 | 这是当前需要解决的入口与职责问题 |
| 所有规则都应塞进 MSBuild | 工程依赖、编译与产物关系适合 MSBuild；行为断言适合 C# 测试；安装事务已有各自实现 | 按职责归位，不把 MSBuild 变成事务引擎或通用测试框架 |
| PowerShell 本身使源码只能在 Windows 开发 | 仓库还有 Windows 进程探测、宿主选择、临时目录等具体假设 | 通用入口使用同一份 PowerShell 7 脚本；保留确有用途的 Windows 专用代码 |

因此，本次并非以“模仿 SMAPI 的所有目录和部署行为”为目标。0.7.0 已有标准工程基础；剩余工作集中在公开依赖、测试选择和脚本职责。

### 2.2 贡献者截图如何使用

截图是对方工作区的自述，未给出准确提交、完整 diff、失败断言和原始日志。本计划将其作为定位线索，不登记为本仓库的 PASS/FAIL 证据，也不据此撤销 0.7.0 验收。

| 安装 DebugConsole 缺少 Author SDK 产物 | 安装测试的前置包不齐 | 从通用构建测试中移出；显式运行安装测试时仍应报告缺少前提 |

| 安装、路径、日志、事务等 Bash 脚本自述成功 | 对方已尝试较大范围，且承认复制了重复逻辑 | 优先提取最小复现和可共用修正；不引入对应的第二套脚本体系 |

这些阻断中，有些对“编译源码、运行通用测试”没有必要；它们对原本的安装、探针或真实游戏测试未必多余。正确做法是明确选择范围，而不是删除保护条件。

## 3. 事项 2：公开源码交付

事项 2 的可实施规则、实际路径核对和接口细节见[公开源码交付具体设计](../reviews/code/2026/20260911-0003-public-source-delivery-design.md)及其规则草案；该设计明确当前 HEAD 与 D7 工作树输入的差异、许可补件、所声明 Windows 构建闭包和 E/P/N 基线生命周期。它仍为 `proposed`，不代表导出器或远端更新已实施；本节保留方案方向，实施细节以该专项设计为准。

### 3.1 内容边界与目录

采用“固定公开边界 + 持续维护公开 main + 普通 PR 回流”。不直接推送整个内部工作分支，也不按版本手工拼一个无法回流的目录副本。

在“工作树与远端推送0910”的目录讨论基础上，保留现有代码路径。把 `author-sdk` 改名为 `sdk`、把 `tools` 改成 `build` 的外观收益不足以抵消 csproj、Import、fixture 和 PR 路径映射的成本；目录说明可以把这些入口讲清楚。

建议的公开树如下。这是目标目录，不表示下面的文件已经全部存在，也不要求先补齐空白教程才能交付：

```text
README.md                      中文主入口：玩家、Mod 作者、仓库贡献者分流
README.en.md                   简短英文入口，避免维护第二套完整手册
CONTRIBUTING.md                 从公开源码开始的开发与 PR 指南
LICENSE / THIRD-PARTY-NOTICES.md
CHANGELOG.md                   已公开版本的用户可见变化
DTMAPI.sln / global.json / Directory.Build.* / 必需构建配置
.github/                       公开 CI、Issue/PR 模板及协作说明
src/                           可公开的框架、SDK、工具源码
tests/                         公开测试、测试分类及允许分发的 fixture
products/                      构建和公开示例需要的第一方源码与合法资产
author-sdk/                    现有模板、schema、targets、作者指南
tools/                         所声明公开能力实际依赖的脚本和工具
docs/zh-CN/                    玩家入口、架构/API 入口、贡献者说明
licenses/                      需要随源码分发的第三方许可文本
```

公开内容遵守以下规则：

1. 代码、工程文件、测试和 schema 在内外保持相同路径及内容。导出器不改写源码、项目引用或版本号；如确需移动代码，在源仓库做一次正常重构，内外共同采用。
2. 公开源码必须包含声明的构建、测试所需的完整依赖。`products/` 不能只为看起来整洁而删掉被工程引用的项目；当前仍消费的旧 target、兼容 reader、第一方冻结 fixture 也不能因名字含 `0.5.5` 被统一删除。
3. 内部规划、Review、Update、月表、运行证据、工作区助手状态、机器设置、游戏文件、反编译材料和未经许可的第三方资料不进入新的公开快照。内部治理测试仍留在内部运行。
4. `.gitignore` 不是公开内容边界；已跟踪的内部文件不会因此自动消失。使用小而明确的目录归属规则和必要例外；新增未分类目录在导出预检中停止，提示维护者分类。
5. 不把整个 `references/` 或所有 ZIP 视为一种类别。公开测试当前需要特定 BepInEx fixture ZIP，必须核实许可并配齐声明；反向整理资料和第三方页面副本则不能只凭来源链接就视为可再分发。无法解决来源的可选材料不随公开树交付，必要依赖未解决时该能力不能宣称可用。
6. 公开根不依赖内部 `PROJECT.md`、当前状态路由或个人助手规则才能构建。当前 UnitTests 用 `PROJECT.md` 寻根，应改为公开且稳定的工程标记，例如 `DTMAPI.sln` 配合 `global.json`，不要为满足这个探测而公开整套内部政策。

目录规则只决定“哪些已有文件可以公开”，不成为第二份工程清单或测试清单。工程图继续由 MSBuild 拥有；测试分类归第 4 节。

### 3.2 固定导出与 PR 回流

内部工作区保留为完整源码及维护记录的集成位置；公开 main 是可独立开发的源码入口。公开路径的实际实现必须及时回流到内部，不能让两个地方各自发展同一功能。

首次与后续交付共用同一导出方式：

1. 选择准确内部提交。预检确认公开范围内的变更全部进入该提交，并将 0.7.0 生产输入与已验收摘要对应。无关的内部工作树变更不混入。
2. 从该提交的 Git 对象读取文件，按固定规则生成公开树；禁止 `git ls-files` 后复制当前工作树、再用 HEAD 充当来源。导出目录与内部仓库、游戏目录和发布目录隔离。
3. 仅根入口说明允许少量固定映射，例如内部保存的公开版 README 映射为公开根 README。其余公开说明采用相同路径。映射不能承担整套手册的逐版改写。
4. 保存上次纯导出基线 `E`，读取当前公开 main `P`，生成新导出 `N`。在创建更新 PR 前，用明确的 `E` 作基线完成 Git 三方比较/合并，保留 `P` 中新增的贡献。不能用目录镜像覆盖公开 main。
5. 正常情况下先把公开 PR 的改动回流内部，再生成 `N`。若公开 PR 尚未回流、两边同时修改、重命名或删除相同内容，应显示差异并停止有冲突的更新，不使用整批 `ours/theirs` 自动裁决。
6. 在最终准备合入的公开树上重新检查内容分类、许可、禁止分发内容和依赖闭包，再运行所需验证；不能只检查 `N`，因为 `P` 的贡献也可能新增未分类文件。通过后形成普通 PR；初次公开内容重排与后续功能 PR 均可审查。

首次没有 `E` 时，固定公开 main 的准确提交作为首轮比较对象，逐项审查目标公开树对旧内容的保留、替换和删除；不把旧 main 假定为已经符合新规则的纯导出。初次 PR 成功合入后建立 `E`。以后每轮成功合入才把 `E` 推进到本轮纯导出 `N`，不能用含有额外公开贡献的合并结果代替，否则下一轮可能误删尚未回流的贡献。

候选记录它所针对的准确 `P`。从验证到合入之间，如果公开 main 有新提交，旧候选必须重新比较、合并并验证变化影响，不能继续按旧 `P` 覆盖更新。检查失败、冲突未解决或 PR 尚未合入时，不推进 `E`，也不改变公开 main。

`E`、准确内部来源以及公开合入提交的对应关系使用普通 Git ref、tree/commit ID 和提交说明保存。纯导出基线需要可恢复，但不能把内部提交设为公开提交的父节点；内部 SHA 可以作为来源文本，内部历史不能因此进入公开分支。不新增一套收据数据库、同步服务或每版手写的来源表。

公开 PR 回流时保留作者和原 PR/提交引用，采用正常 cherry-pick、补丁或三方合并。涉及仅公开根说明的少量映射由同一配置反向定位，不再维护另一份路径表。验证必须覆盖公开改动、内部改动、同文件冲突、重命名和删除；冲突输出供人工处理。

现有 `update-audit-package.ps1` 不能直接充当该导出器：它从文件清单复制工作树，且整类排除 ZIP，不符合准确提交与依赖闭包要求。实现可以复用合适的底层文件工具，但入口语义必须分开。

此前讨论中的 `agent/dtmapi-0.7.0-source` 和 `v0.7.0-preview` 只作为已发生的远端交付记录。新的 0.7.0 main 候选必须来自最新验收基线。默认通过普通 PR 更新公开当前内容，保留已有公开历史及标签；“重新设计公开内容”不等于允许强推清史。新的快照不会自动清除旧公开历史中的文件，若另有历史清理需求，应单独确定对象和操作。

### 3.3 公开说明与许可维护

首批只做实际使用所需的入口：

- 玩家从哪里取得包；Mod 作者如何进入现有 Author SDK；贡献者如何从干净克隆开始。
- 0.7.0 的源码范围、Windows 开发前提、公开测试命令、哪些验证需要维护者环境。
- 项目职责和 API 文档入口；编译、测试、SDK 打包、安装到游戏、真实运行之间的区别。
- 提交 PR 所需的变更说明、测试范围及结果；不要求外部贡献者制作内部 Update、月表、游戏收据或完整 Release 证据。

文档只保留一个内容来源。已有 `author-sdk/` 作者指南继续拥有 SDK 使用事实，仓库入口链接过去；未来包内指南从同一来源复制。不得在公开 README、SDK ZIP、内部手册分别手改三份同样的步骤。版本、命令和 schema 示例尽量引用现有版本配置和实际 CLI，不新增另一套版本配置。

0.7.0 已验收 D7 的 ZIP 保持原身份。此次重写公开仓库说明不强制重包 SDK；以后若替换随包说明，必须登记为新的准确产物，按变化检查内容和包完整性，不能仍宣称 ZIP 与 D7 相同，也不因纯说明修改机械重跑游戏。

中文说明先核对产品事实，再按用户要求用 `humanizer-zh` 润色，最后检查命令、文件名、版本号、链接和边界没有被改义。许可证原文、第三方版权文本和代码不做这种文风改写。英文只保留入口和关键限制，暂不引入每版全量双语同步。

保留当前项目的 MIT 许可选择。第三方依赖按实际分发内容记录许可、归属和必要声明，不笼统标成 MIT。当前根 NOTICE 对 BepInEx 是否随源码提供的表述与 fixture 情况需要统一；来源清单不代替分发许可。首次完成盘点后，只在依赖或分发内容变化时更新，不逐版重做全部历史资料审查。

## 4. 事项 3：0.7.1 的有限 Linux 构建与通用测试

### 4.1 一套分类，几个可解释的入口

在现有 `tests/DTMAPI.UnitTests/suites.json` 基础上扩展分类和选择能力，复用已有 suite/focus 的身份。公开性、平台和所需环境是不同维度：公开的测试也可能只能在 Windows 运行；纯 C# 测试也可能读取内部历史材料。

每个可独立运行的测试集合声明：项目或既有执行入口、可公开性、支持平台、必需工具/fixture，以及是否需要真实游戏或内部验收输入。profile 仅按这些属性选择，不各自复制项目清单和规则。迁移现有零散测试列表时保留原 ID 和 focus；无分类的新集合必须提示补齐，不能默认加入 Linux，也不能悄悄丢出 Windows 覆盖范围。

| Profile，名称为拟定 | 职责 | 不应要求 |
| --- | --- | --- |
| `Generic` | 公开的、无游戏依赖的构建和通用行为测试；Windows 与 Linux 共用 | Steam、注册表、私有 ABI、真实存档、维护者历史证据、预先存在的本机 artifacts |
| `PublicWindows` | `Generic` 加公开且必须在 Windows 验证的集合 | 内部规划、私有游戏材料、维护者完整 Release 收据 |
| 既有维护者/Release/游戏入口 | 保留内部治理、准确历史包、私有 ABI 和真实游戏验证 | 不为了 Linux 支持改变原判定规则 |

具体实现优先扩展现有 `test-public-source.ps1` 及共用测试助手，保留现有 Windows 默认行为的含义，并把内部专用检查路由回既有维护者入口。公开范围的变化必须列出迁入、迁出项目及其新归属，防止借分组删除覆盖。

拟定的使用形式如下，尚不是当前可用命令；参数名在实施时确定一次，并与帮助、CI 同步：

```powershell
# 只构建 Generic 所需源码；项目引用由 MSBuild 求解。
pwsh -NoProfile -File tools/scripts/test-public-source.ps1 -Profile Generic -BuildOnly

# 在同一入口完成构建和 Generic 测试。
pwsh -NoProfile -File tools/scripts/test-public-source.ps1 -Profile Generic
```

当前测试包含自定义 C# 可执行测试集合，不能因为 `dotnet test` 返回零就宣称这些集合已运行。此次不迁移整个测试框架。贡献者可以用标准 `dotnet build <所选工程>` 做普通工程构建；仓库推荐入口负责准确选择与执行测试，并打印实际使用的 .NET 主机。根目录无参数 `dotnet build`/`dotnet test` 的全仓库行为不在首轮 Linux 承诺中。

### 4.2 首轮范围与修正顺序

现有默认 Unit suite 共 15 个，8 个标为不要求 Windows：`moresaves`、`core`、`runtime-integration`、`compatibility`、`animalhusbandry`、`autofishing`、`autoharvest`、`oil-content`。这些只是首轮候选，不是已经通过 Linux 的清单；`runtime-integration` 的名字本身也不代表它必须启动游戏，应按实际依赖判断。

先在这 8 个集合中确认公开闭包和平台假设，再加入确有价值且可独立运行的 C# 工具/SDK focus。Windows 专用单测仍留在 `PublicWindows`。如果一个集合混合两种前提，沿既有 focus 或测试职责作最小拆分，避免把整个集合排除后宣称已支持。

| 当前需检查的位置 | 有界处理 | 不扩大到 |
| --- | --- | --- |
| `common.ps1` 的 .NET 与 PowerShell 主机选择 | 继续由 `Get-DotNetExe` 验证仓库 `global.json` 约束；Linux 初期要求预装兼容 .NET 8 和 PowerShell 7 | 不凭 PATH 顺序或 Major roll-forward 换主机；不新增复杂 Linux SDK 安装器 |
| `test-common.ps1` 的 `Get-CimInstance Win32_Process` | 通用测试前提不调用 Windows 进程枚举；真实进程控制按平台能力声明 | 不放宽现有游戏并发保护，不为通用测试建立 Linux 游戏进程管理器 |
| `DtmApiTestSession.cs` 只管理 TEMP/TMP | 核对并补齐 TMPDIR、临时根选择与环境恢复；测试输出使用隔离目录 | 不更改机器全局环境和目录权限，不写入 Windows/WSL 共用的 bin/obj |
| QA 测试的 `pwsh.exe`、固定分隔符和子进程假设 | 由共用宿主解析和路径 API 处理，核对退出码与参数传递 | 不新增每平台一份同名断言 |
| SDK `OfficialLocalTests` 的 Windows sharing violation 32、net48 Harmony fixture | 保留 Windows 归属；抽出可独立的通用部分时维持负例强度 | 不把改后缀等同于移植成功，不强行模拟 Windows 文件锁语义 |
| 源码 `.Contains` 与具体脚本路径绑定的断言 | 对移动助手引发的脆弱检查，改为可观察行为或正确模块边界；真实架构/安全约束继续保留 | 不批量删除源码契约，不修改 receipt/Catalog/ABI 规则来换取绿灯 |
| Catalog 校验混合结构规则与历史证据路径 | 公开侧保留 schema、ID、引用闭包等规则；历史 Update、本机游戏事实归维护者检查，共用底层规则 | 不公开整套维护历史来满足通用入口，不为 Linux 建另一套 Catalog |

生成选择性 `.slnf`/项目构建时复用现有 `Invoke-DtmApiTestProjectBuild`；MSBuild 继续处理 `ProjectReference`。修正其跨平台路径或启动假设即可，不手写新的编译顺序。

### 4.3 结果不能含糊

选择测试前就列出纳入和不纳入的范围及原因。未被 profile 选择的 Windows 游戏测试应标为“不在本次范围”，不能出现在 PASS 数量中。

- 被选择的集合缺少公开文件、工具或必需 fixture：报告缺少前提并返回非零；导出器遗漏文件也属于这种失败。
- 显式点名了不支持当前平台的 suite/focus：运行前拒绝并解释，不自动换成一个更小的测试集合。
- 已开始执行的断言失败、异常退出或超时：保持失败；不能自动改标为 skip。
- 被选集合全部执行通过：只能报告该 profile 通过，同时给出执行、排除、失败数量；不能写成“完整仓库测试通过”。

### 4.4 脚本拆分范围

PowerShell 保留命令调用、环境适配和流程编排。C# 工程图归 MSBuild；平台无关的产品规则和复杂行为断言优先复用已有 C# 实现与测试。可以有 PowerShell 自身的测试，是否需要拆分应看职责和重复规则，不能以“脚本有测试”为不合理的证据。

首轮拆分只服务这次公开构建与通用测试：从 `common.ps1`、`test-common.ps1` 中划出仓库/工具链、通用测试进程及临时目录能力，保留现有入口签名。只有确实阻碍该目标的 Catalog/源码契约耦合才同步拆解。`test.ps1` 保留维护者顶层编排，不复制给 Linux；已经模块化的游戏烟测不列入整治工程。

`common.ps1` 及 release helper 目前会被复制到玩家包。实施前必须确认抽出的模块是否被这些入口消费，并检查准确包中的导入闭包。优先让开发专用入口引用开发模块，避免玩家安装器加载完整开发工具链；必须随玩家包带上的共用模块由原打包清单统一纳入，不再人工复制两份。

拆分不得给游戏加载程序集增加新依赖、常驻服务、启动扫描或每帧工作；玩家不因这项计划而必须安装 PowerShell 7 或 .NET SDK。Windows PowerShell 5.1 的既有玩家入口兼容性仍须保留。若要改变安装事务、运行时生命周期、Native/Hook 或存档语义，停止扩大此项任务，转为独立产品变更。

## 5. WSL 验证和开支

本机只有 WSL，足以开展首轮 Linux 原生工具链验证。使用 WSL2 的一个明确发行版，在 Linux 文件系统内建立独立克隆，例如 `/home/<user>/src/DTMAPI`，不直接复用 Windows 检出的 `bin`、`obj`、临时目录或包缓存。

调用 Linux 的 `dotnet` 和 `pwsh`，记录可执行文件路径、版本、发行版、准确提交和 profile。排除通过 WSL 互操作误调 `dotnet.exe`/`powershell.exe` 而产生的假 Linux 结果。这里的“Linux 原生”描述构建和测试进程，不表示 Windows 游戏变成了 Linux 原生程序。

首轮必须在同一源码提交上完成 Windows 与 WSL 的 `Generic` 验证，覆盖所选源码的 Debug/Release 构建，以及路径大小写、空格/中文、临时目录、子进程、失败清理等本次改动触及的行为；既有 Windows 专用测试按影响范围补验。无需为这项计划重测全部产品游戏场景。

| 成本 | 设计约束与记录方法 |
| --- | --- |
| 玩家游戏运行开支 | 不增加游戏路径代码或依赖；通过变更范围与包依赖核对确认。不能把“设计上不新增”写成已经做过性能测量 |
| 本机开发开支 | 一次 Linux SDK/pwsh 安装及独立 NuGet/构建缓存；记录冷恢复、温构建和通用测试耗时、缓存/产物体积 |
| Windows CI | 使用现有公开工作流；按变更路径选择检查，一次构建复用输出，不默认执行完整 Release/SDK 重包 |
| Linux CI | 首轮 WSL 足够；必要时在同一工作流增加一个手动、非必需 Linux 任务，复用入口与输出格式，不建定时矩阵 |
| 长期维护 | 新 suite 一次分类，依赖变化一次核对；不每版维护 Bash 镜像、双语全文或独立 Linux 基线 |

首轮实测后再决定是否值得常开 Linux CI。不预先承诺免费、加速倍数或固定运行时长。若冷启动主要花在与通用测试无关的 SDK 便携工具链、历史包和游戏材料上，应先纠正测试闭包，而不是继续增加缓存和环境模拟。

对 Windows 后续开发的直接帮助是：公开源码可重建、测试入口可解释、编译依赖不重复维护、贡献者修改容易回流。Linux 还会暴露原本无必要的路径和进程假设。对 Steam Deck/Proton 玩家，本计划没有直接的运行兼容承诺；可能间接受益于通用文件处理修正和更多贡献，但是否能安装、注入和稳定运行仍取决于另行验证的玩家包与游戏宿主。

## 7. 验收、回退与日常维护

### 7.1 实施时的最小检查

| 变更 | 需要的检查 | 不自动触发 |
| --- | --- | --- |
| 纯公开说明、文风或链接 | 核对事实、命令和链接；命令或环境前提变化时才补对应验证 | 重复导出、Git 冲突用例、Windows 全部公开测试、游戏验收 |
| 公开目录边界、导出器、回流逻辑 | 来源与许可清单；重复导出一致；新公开树的依赖闭包；Git 回流与冲突用例；干净 Windows 公开流程 | 全部游戏验收、Steam 上传、SDK 重包 |
| Generic 选择、路径/工具链、测试助手 | 同提交 Windows/WSL 所选构建与通用测试；错平台、缺前提、断言失败不得返回成功 | Linux 游戏安装、烟测、完整 SDK 作者链 |
| 被玩家脚本消费的共用模块 | 从准确打包树验证导入、PowerShell 5.1/既有宿主兼容及对应合成测试；事务行为变化时补对应测试 | 未改变生产输入时的整轮游戏回归 |
| 生产程序集或真实打包语义发生变化 | 按现有产品工作流选择准确受影响的检查与必要 Runtime 验证 | 以“只是支持 Linux”为由免验或无范围重跑全部项目 |

测试分类、导出闭包和回流逻辑需要行为测试，因为错误会造成假通过或丢失贡献；纯文风、路由链接和低影响说明修改不增加镜像断言。公开文件遗漏不能靠放宽测试来绕过，内部材料退出公开树也不能靠删除对应内部检查来实现。

验收完成时，应能交回：准确的 0.7.0 公开更新候选、可复用的导出及回流入口、单一测试分类、Windows 干净克隆验证、WSL 的实际 Generic 范围和结果、中文贡献指南、一次实际开支记录。没有这些结果前，文档不得将计划状态改成“已支持 Linux”。

### 7.2 正常更新周期

公开 PR 先按公开 profile 验证；其修改回流内部后，再按是否涉及产品行为补既有检查。下一次源码更新由准确内部提交生成 `N`，与 `E/P` 比较并准备普通 PR。发布说明只更新实际行为变化，版本事实使用既有来源，公开目录规则只在归属变化时修改。

维护者不需要每版重读整个内部历史、手工复制测试清单、翻译所有脚本或在 Linux 重打 Windows 发布包。内部 Update/月表仍按现有规则记录实现；外部 PR 只提供正常的说明和范围证据，维护者整合时归入自己的实施记录，不增加第二套外部治理账本。

若 Linux 局部适配成本超出预期，保留已完成的公开源码与 Windows 流程，把未完成的 Linux 集合标成未支持，停止扩大范围。已经明确承诺的 Generic 失败仍需要记录和处置；可以延后修复，但不能以“非发布门禁”掩盖结果。

导出器故障时停止更新，保留当前公开 main 与上次基线；不回退成覆盖式复制。目录或模块拆分有回归时通过普通提交撤回该有界修改，保留测试结果与来源。不移动既有标签，不覆盖已验收包，不恢复被拒的 Bash 双轨方案作为默认退路。
