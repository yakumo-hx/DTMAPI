# DTMAPI 长期工程路线与发布版本

- Lifecycle: accepted-design
- Role: 阶段、依赖、可发布范围和复盘的唯一路线。任务规格在 [tasks](tasks.md)，进度在 [status](status.md)，近期实施细节在 [execution-sdk-msbuild](execution-sdk-msbuild.md)。
- Revision: 2026-09-10，增加后续方法验证，解除无必要的能力依赖；0.7.0 新增 PN-042 现有 Mod/接入兼容门。保留 0.6.X → 0.7.X → 0.8 清退安排，历史验收不改写。
- Evidence: 最新 [SDK 首发/CSV 事实更正](../../updates/2026/20260910-0011-sdk-first-release-plan-correction.md)，承接方法与 SDK 架构 Review。版本是目标安排，实际发布仍由 Catalog、release Update 和产物证明。

## 当前为什么先完成 SDK 架构收口

M1–M3、委托/Native 泛型/普通库等增量已经有界验收。r5 的 EditorConfig、主 Mod 框架常量、语言版本对照表明，自有工程解释器仍让普通作者语义偏离标准，并会把生成器、资源和依赖不断变成专用适配任务。统一构建应该以标准 MSBuild 为基础；冻结引用、交付检查不依赖自有编译组织。

因此 PN-041 从后续可选原型改为首发前完整改造：标准工程/工具链→恢复/生成/诊断→准确 pack/Native→迁移/实际 IDE/CI→完整 SDK→Mono/兼容与一次正式切换。首发前修正基础可避免作者先采用一套即将放弃的工程规则。M4 原生实验没有技术上新增的 SDK 依赖，但本次实施优先完整收口 SDK，然后继续 SaveData/内容/Host；不扩成 Runtime 大重构，不等待所有 NuGet/IDE/设备支持。

## 可发布版本

在已有 R 节点先完成 [方法比较](method-validation.md)，再实现和冻结公共契约。保存/内容/Host/领域/UI 的原生优先对照保留。0.7.0 是首次 SDK 公开交付，PN-041 不再承担通用旧 SDK 迁移；[PN-042](execution-compatibility.md)核对真实旧包/来源，有新退化才修正。CSV 属于已授权删除的第一方临时接口，保持删除，不阻塞首发。

内部开发在首发前只推进 0.6.X；原版本归位已完成，下一未占用候选由版本源和 status 确认。0.7.0 是完成 M3 后的第一个公开版本，M3 只是最早能力门，还需要首发候选的安装/升级/支持与实际产品验收。验收发现问题允许吸收后续的必要修复或独立完成的功能后再发，不为赶版本删减 M3。0.7.0 尚未发布时，不把下一包叫作已经发布的 0.7.1。

0.7.X 是 pre-1.0 的持续公开交付线：新增能力可随补丁号发布，但对已声明支持的 API 保持兼容加法；具体能力仍受其稳定性限制。上表是内容分组，不是不可变日期/包名：紧急修复可占用额外 0.7.X，功能版本顺延；数据/内容分支也可按证据调序。每次公开新 target 冻结之后不能原地增加或换掉载荷。

0.8.0 的清退条件不依赖“把所有类 SMAPI 能力都写完”。0.7.4/0.7.5 的远期领域可按实际优先级调整，PN-033.a/b 必须先做，之后到达公告窗口即可进入 0.8。Runtime release、API target、SDK tool、assembly identity 和 schema 仍是不同坐标，不能用一个版本号替代所有兼容判断。

首发验收中若吸收 PN-037 等后续能力，更新该候选实际范围，补相关测试；已经被 0.7.0 吸收的任务不在 0.7.1 重做。具体上传始终是用户对可审阅发行结果的最后授权，规划不是自动发布许可。

分发按 [SDK 发布流程](../../workflows/author-sdk-release.md)拆为作者 SDK 独立附件与两个玩家 Runtime 包。0.7.0 同步更新多平台安装渠道须完成 PN-031.multi；旧 0.6.1 多平台证据不能投影为新包通过。该发行切片与 M4 互不等待，不将安装器工作重新包装成 SDK 能力建设。

## 可以连续执行到哪里

本批为 [PN-041.a–f](execution-sdk-msbuild.md)＋[PN-042](execution-compatibility.md)：先薄集成和真实旧包/入口基线，再完成标准构建与当前内部输入转换，只有具名新退化才做 042.b。共用一份实施 Update，最终一次完整 Release/准确游戏组合；无问题不为兼容卡创造修改。前步源码完成即可继续实现，最终证据 pending 不制造循环。本批完成统一交回，不自动上传或扩成 M4。

按用户选定模型在同一任务实施和完成有界复盘；以后 Sol 使用同一规格，在下表的设计关口携带具体证据切回 GPT-6。R-AuthorBuild 不重新选择后端。只在真实长期公共承诺需要用户决定、必要外部条件在独立工作完成后仍阻塞，或详细输入耗尽时交回。发布/玩家反馈待办不能阻止无此依赖的内部工作。

## 更远能力地图

[C01–C33](capability-map.md)继续覆盖完整成熟度：作者工程/调试、隔离与协作、配置/输入、可靠持久数据、资源与内容编辑、Host/Pack、领域查询/事务、UI/音频、持久实体、升级/诊断/性能与维护。扩更多资源/实体家族、真正 debugger、结构代理、profiling 分别按真实需求和证据推进；源生成器的普通工程接入已纳入 PN-041 首发范围。

多人、跨游戏、在线更新/崩溃服务、可视内容编辑器仍是条件性产品方向，需游戏事实和维护成本决定。“类 SMAPI”不自动承诺这些能力，也不意味着复制 MonoGame 或前作接口。
