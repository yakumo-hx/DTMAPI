# 后续能力的方法验证

- Lifecycle: `accepted-design`
- Role: 在大规模实现和首次公共契约冻结前，比较实现方法。以下 V 标识是已有 PN / R 节点的实验规格，不是新任务队列、审批流程或凭证系统。
- Decision: [本次路线复盘](../../reviews/code/2026/20260910-0005-platform-method-validation.md)。状态只在 [status](status.md)，执行顺序和发布安排只在 [roadmap](roadmap.md)。
- Evidence boundary: 本轮完成源码和历史研究核对；以下新增原型均未实测通过。SDK 的标准编译原型有既有证据，完整交付仍待 PN-041。

## 怎样避免下一次绕路

先固定作者需要完成的旅程及不能破坏的旧行为，再比较实现。优先检查标准工具链、游戏已有能力和现有平台服务能否承担责任；需要新增机制时，明确它填补的实际缺口。不能从“统一、可控、确定性、事务”这些目标直接推出必须自建解释器、存储系统、编辑器或 UI 框架。

每个适用节点只做一个有代表性的垂直原型，必要时加入第二作者/修改者和一个最容易推翻方案的反例。允许实验选出“现有原生能力已经够用”；这仍是完成目标，不需要为原型创造新公共 API。普通内部重构、已验收入场机制和每个 bug 修复无需重复此过程。

在该任务现有 Update / R 结论内回答五件事即可：

1. 作者通过公开入口完成了什么；还需学习哪些专用规则、重复声明或手工步骤？
2. 哪些能力由标准/原生机制直接保证，哪些只是 DTMAPI 的推断？最早反例实际结果是什么？
3. 对旧包、原接入方式、原生保存/复制/备份、停用和升级有什么影响？
4. 新增多少需要长期维护的 native 接缝、独立状态来源、公共格式和恢复操作？实际耗时、内存或包体成本是多少？不以代码行数代替成本。
5. 采用哪一条、舍弃哪一条、尚不承诺什么；实现哪些任务，何种具体反证才重开？

不要求同时把所有候选做成产品。先做最便宜且最能证伪的实验；已被原生事实排除的方案记录依据即可。原型成功后，选中路径还须通过原有完整产品验收。失败先缩到受影响能力/后端，继续独立分支；不能悄悄降低数据或兼容承诺，也不能仅因为第一个方案失败就升级到更复杂框架。

## V-Build

**挂接：PN-041.a / R-AuthorBuild.build；详细步骤归 [SDK 执行包](execution-sdk-msbuild.md)。**

标准 MSBuild 单后端已决定，不重新投票“是否维护 csproj 子集”。需提前验证的是薄集成能否成立，而非到 a–e 全写完后才发现 IDE/工具链边界不通。

- 用同一个最小 Strict＋普通库工程，先打通标准 Csc 冻结引用、一个实际 IDE 的设计时引用与 Build、CLI 的同一工程；比较可复用的 props/targets＋子进程桥和必须的 task adapter。优先现有标准扩展点，只有宿主事实要求才增加 adapter，不重新组织 Csc。
- 同版本标准 SDK 的便携目录与显式选择的已安装目录分别验证解析、global.json、缺工具错误；测完整作者包体积、解压空间和基础离线输入。便携完整包仍是 0.7.0 推荐分发，工具链发现不成为永久 ABI；不因此新增第二 SKU 或第二后端。
- 用一个当前仍使用的内部工程验证输入转换、标准常量/EditorConfig、工具项目与运行项目 TFM 分工。旧 SDK 从未发布，不先建设通用迁移器。复杂 generator/pack/Mono 完整证明仍在 b–f，不能以小原型取代。
- a 的实际 IDE 骨架不通时先定位宿主/引用/扩展接缝，不写完大批专用 adapter 再补救；暂时缺 IDE 工具可先推进独立 b/c，实际 IDE 门保持 pending。缺自动化工具本身不是 shipping IDE 不支持的证据。

**出口：** 选定薄集成和工具链解析方法，带实际作者工程结果继续 b–f。若只需内部接线修正，同任务完成；只有反证要求破坏长期支持/兼容承诺才交回。保留 SDK 的交付检查，不增设作者输入签名或证明编译执行的独立凭证家族。

## V-Compat

**挂接：PN-042.a，0.7.0 独立兼容门；完整矩阵归 [兼容执行包](execution-compatibility.md)。**

用准确公开 0.6.1 和固定现有 Mod 对照候选，分别观察来源选择、准入、程序集绑定和真实行为。不能将所有差异归为 SDK 问题，也不能用新编译样本代替旧二进制。已支持的旧包无需重新编译、重新生成 receipt、修改 manifest 或迁移来源；正常冷重启边界保留。

用户已明确 CSV 是第一方临时接口，删除有效；撤销其方法比较与恢复任务，保留精确允许集合。旧 SDK 从未公开发布，也不构成旧作者客户端/通用迁移义务。先区分已发布 Mod/Runtime 契约、内部工具输入与已授权退役，避免为不存在的承诺做兼容工程。

**出口：** 发现真实新增退化时确定最小修正进入 PN-042.b，否则直接 c；与 PN-041 最终候选合并验收。冻结证据不原地冒名改 hash；确有 Runtime 修改才更新两投影，不为 CSV 或内部 SDK 强制重建 Runtime。

## V-Save

**挂接：PN-024 / R4a，随后 PN-012；实验操作与故障窗口归 [M4 实验](m4-experiments.md#r4a保存身份与提交窗口)，语义归 D02 / RT-07。**

| 方法 | 实施前要证明什么 | 当前处置 |
| --- | --- | --- |
| 官方通用扩展字段 | 当前游戏确实提供，原生保存、复制及缺 Runtime 重存保留 | 有界核对；未找到不能推导所有同档容器都不存在 |
| 现有同档字符串容器 | `cityData.dialogueManager.variableStorage` 的未知命名空间值不被 Yarn 初始化、对话或缺 Runtime 重存清掉；无剧情副作用 | **最先实测的候选**，尚未接受为公共后端 |
| 同档新增字段/序列化适配 | typed load/save、加密、版本回退与缺 Runtime 能保留；不靠全局侵入才能成立 | 仅在前者不适合且有具体收益时做受限原型，不能只往 JSON 加字段就宣布成功 |
| 外部 sidecar＋journal | 独立载荷与 native 的提交关联、身份、复制/回滚、相同 native 字节、映射丢失和冷恢复可以判定 | 保留完整既有实验作候选/兜底，撤销“先把协调器写完”的默认顺序 |

最早实验：在隔离可处置槽写入两个 owner 的无玩法载荷，保存后彻底退出；移除探针/Runtime，以原版冷加载、触发对话并重存，再启用读回。未知值丢失、类型重写或剧情副作用即否决该容器。成功后再扩容量、命名空间/类型碰撞、schema、新建/复制/删除/备份回滚、未保存退出、原生失败和中断窗口。遵守 PROJECT 的授权槽/云隔离和锁要求，不用玩家活档。

**选择：** 优先能让 native 保存同时承担 Mod 载荷提交、复制和回滚且实际可靠的后端。若同档成立，不再给每个 owner 建外部 journal；sidecar 必须人工认领的情形计入玩家成本，不能包装为透明保存。公共永久 SaveIdentity、复制谱系和物理布局暂不冻结；正确绑定当前档和 owner 是要求，暴露永久 ID 不是默认要求。

**兼容：** 新通用 SaveData 的后端选择不迁移或删除 MoreEquipment 的既有 sidecar/退物恢复，也不改旧 SaveSaving fail-closed。产品数据的后续迁移单独验收。

## V-Content

**挂接：PN-013 的只读/资源段与 R4b；完整效果实验归 [M4 实验](m4-experiments.md#r4b一项展示表字段与一种静态图标)。**

先复用已选 stone 展示文本、自制 icon、官方覆盖控制组和两个作者：A 直接官方 JSON/PNG，B 官方原生语义＋来源/校验/owner 薄适配，C 仅对 A/B 无法满足的需求提供受限编辑。比较作者实际声明数量、启停/排序、错误定位、撤回、旧 DTO/已显示 Image 与新读/重开后的效果、内存成本。A/B 达标即可形成该能力；不因缺通用回调 API 判失败。

若选 C，保留深层修改后抛错、后续 editor 只看到最后成功状态、资源释放及传播成本验收。做不到隔离的类型只能只读或明确重载；不能把“缓存失效”称作所有活对象自动更新。优先局部、类型专属快照或声明式变更，不先设计任意 Unity 对象深复制。

ModContent 只读包输入可先成立，不等 GameContent。图像/音频先比较简单 owner 持有和释放与真正需要共享的租约；只有存在已证明的共享/跨代消费者需求才建立引用计数或资源依赖图。不会共享的资源不为将来假想复用增加公共 lease 协议。

**出口：** 记录确切支持家族、原生/DTMAPI 的责任和刷新规则后冻结对应公共面；不预先固定通用 AssetKey、编辑优先级/回调或全局传播图。

## V-Host

**挂接：PN-025；依赖 PN-011＋PN-013 只读包输入/owner，原生 Host 另依 PN-010。**

先让仓库外一个普通 Host 消费两份独立 Pack，使用只读文本/翻译/资源或已存在的窄 native 能力，比较现有包/依赖/owner 上增加绑定与新增平台补丁 DSL。默认前者；具体增改删、条件表达式、领域 schema 由 Host 选择。平台首次 Host 绑定不等待完整 GameContent，只有用到编辑的 Host 追加该依赖。

验证 Host 缺失/版本错误、单 Pack 坏数据、Host 失败/停用、Pack 更新与双 owner 清理，实际效果和撤回分别观察。当前游戏会自动扫描官方 `Content` 的 JSON/PNG；受 Host 控制的新 Pack 必须在 Host 不活跃时**原生侧也无效果**，并避免双重加载。比较非自动扫描的包内资源路径和必要的窄接缝后选择，不能只靠 Core 的 inactive 状态。

**出口：** 一 Host 两 Pack 完成公开 SDK 到实际使用，冻结最小绑定/版本/归属契约；不附带冻结平台通用 DSL。已有官方 Content 和混合代码包仍可沿原接入方式使用。

## V-Domain

**挂接：PN-027 / R5 的领域部分；只读查询不等完整 M4。**

按两个真实消费者选择一个领域，先比较原生已有单次操作＋结果核验与自建跨系统事务。背包满、资源不足/部分可用、重复命令、同帧变化、场景失效和不保存返回是最小反例。默认尊重原生操作语义；只有确实跨越不能协调的原生边界且产品需求成立，才设计有限补偿/事务。

**出口：** 冻结 ID/snapshot/availability 和已证明的操作结果。不能把一次 native 调用包装成无证据的“全有或全无”；保存依赖按数据归属追加，不能把所有 mutation 一律阻塞在通用 SaveData。

## V-UI

**挂接：PN-028 / R5 的 UI 部分。**

两个外部作者分别做状态 HUD 和交互面板，比较扩展当前 ConfigMenu/游戏已有窗口与控件的薄适配，和新增窄声明式组件树。先核对当前游戏 UI 的可复用性、许可边界及更新接缝，再写渲染框架；声明式树是候选，不是既定产品目标。

实际记录作者代码/配置、翻译、焦点/输入占用、应用/取消、缩放与分辨率、返回标题及 owner 关闭的资源清理。既有 PN-037 绑定/方向导航事实保留，未测实体手柄仍实验；不能为了本比较重做输入系统。

**出口：** 先固定 owner、焦点、关闭和支持场景，再决定需要哪些公共控件/布局。高级自绘和完整 UI 编辑器不是两个样例的默认依赖；不向 Strict 公共面泄漏 raw Unity。

## V-Entity

**挂接：PN-029 / R5；先选一个原生已有有限家族。**

比较 A 官方 schema＋原生创建/保存，B 仅为原生缺少的附加状态提供 Host 服务，C Host 自有稳定实例模型＋完整重建。默认从 A 验证，不因 Frozen CustomEntity 有壳就选 C；如果原生保存已有实例，不能再 sidecar 保存一份然后重新生成。

原型完整跑获得/放置、换场景、保存/冷启、移除/恢复 Pack、升级与失败创建；记录缺包时原生如何保留/丢弃数据。A/B 不能满足需求才评估 C。缺包会静默丢原生内容时，先决定安全缺失策略，不冻结永久实例/迁移格式或宣称实体平台成立。

**出口：** 只接受该家族。PN-012 仅在 Host 需要额外随档状态/自存实例时成为依赖；任何方案都须真实原生保存和缺包验收。领域 AI/平衡仍归 Host/产品。

## V-Assets

**挂接：PN-040.b / R-Assets，或后续有明确需求的资源类型。**

沿标准 NuGet 的资产选择，先选一个较低 TFM/facade 组合做实际宿主调用和旧包控制，再决定支持切片。比较宿主已提供能力/标准解析与新增装载 shim；不因某包无法运行便先做通用 IL 重写、任意 DLL 隔离或双运行时。不同 ref/lib 已属 PN-041，不重复立项。

工具 graph 与进入游戏的 runtime closure 分开；新运行 TFM 例外必须明确到适用资产，并验证实际 Mono/BCL/共享身份、升级和冷重启。标准 restore 成功不代表宿主兼容；必要依赖确实不能共存时说明限制，保留 Advanced 宿主引用的已有出口。

## V-Maintain

**挂接：PN-032 / R6；逐个具名维护问题进入。**

先用现有 Release/focused/Doctor、固定外部作者 corpus、游戏日志与可用 profiler 形成可重放问题和基线，再比较是否需要新增自动化/指标服务。测真实启动、帧/分配、owner 卸载、资源缓存增长和退出；预算以实测可接受旅程和机器范围形成，不能先写任意阈值再造平台。

版本适配先做薄 capability/probe 和旧行为回归，只有同一边界存在真实不可统一语义才拆 adapter；不默认每个游戏 build 一整套 GameBridge。离线报告可解决的问题不预设服务器/遥测账户。多人、跨游戏、在线支持、可视编辑器分别需要游戏能力和真实用户需求的小型对照，才从远期方向进入任务；当前不预造这些基础设施。

## 与发布和连续实施的关系

近期先 PN-041.a 的 V-Build 和 PN-042.a 的兼容基线；随后同任务推进 SDK 与必要兼容修正，在准确最终候选集中关闭 B / C 验收。0.7.0 因这两个未完成首发门暂不放行，不需要等待所有未来方法实验。

M4 开工即先 R4a/R4b 的方法段；结论支持，在同任务完成选定方法的失败验证和对应实现。保存受阻可继续内容/Host，内容编辑受阻可继续只读包输入/Host，原生保存的实体不被外部 sidecar 技术性卡住。首次公开新契约前 GPT-6 按具体 R 节点复盘；内部接线/有界反例已在规格内时执行者直接决定并记录，不逐步找用户确认。

本批 SDK＋兼容详细任务完成后统一交回。后续方法段已可执行，选定方法后更新其现有实现卡的具体落点再连续推进；如果结果需要新公共承诺或尚未细化的第二套架构，携原型和反例回到对应 R 节点，不把规划中的候选当已批准实现。
