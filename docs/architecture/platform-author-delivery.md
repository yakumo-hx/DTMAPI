# 作者工程、交付与长期维护架构

- Lifecycle: `active`。
- Role: [平台主架构](platform-next.md)的作者工程与交付领域设计；拥有本领域的构建、调试、诊断、兼容与维护目标语义。它描述已接受的目标，不能证明代码、候选包或已发布产品已支持。
- Execution: [实施入口](../planning/platform-next/README.md)、[任务规格](../planning/platform-next/tasks.md)与[唯一任务状态](../planning/platform-next/status.md)。本页不保存执行进度。
- Evidence: [能力地图](../planning/platform-next/capability-map.md)和[能力验收规则](../planning/platform-next/acceptance.md)区分源码、作者、游戏与发布证据；实际结果归对应 Update、API matrix、smoke 与 release authority。
- Current package/API target facts: [SDK target catalog](../../author-sdk/target-catalog.json)、[SDK 作者入口](../../author-sdk/README.md)、[Runtime 版本来源](../../tools/release/dtmapi-runtime-version.props)。已冻结载荷保持不变；候选目标不等于发布承诺。

## 1. 产品承诺及建设顺序

成熟作者体验的最小闭环是：一个不拥有 DTMAPI 仓库的作者，拿到 SDK 和公开资料，创建自己的 ID，编译、运行、诊断、修复、打包，并在之后升级自己的项目与已发布用户的 Mod。维护者不能成为每次编译、原生准入或发布元数据生成的人工依赖。

M1 先修配置正确性并证明现有 API 的真实作者回路；PN-015 收敛构建与 SDK160 引用校验语义，PN-004 完成官方 Local 开发安装，PN-016 固化生命周期证据，PN-017 完成作者诊断与调试能力边界，PN-008 验收实际作者与 Mono 流程。可选服务与反射按主路线随后建设；第一条作者验收不依赖反射。M2 收口生命周期、调度和基础服务，M3 解决开放原生引用、依赖库、跨 Mod 合作和工程扩展，M4/M5 的数据、内容和领域能力必须同步交付可独立消费的作者样例。M6 收口长期兼容与发行维护；其基本设计和证据积累从 M1 开始。

内部依赖可并行准备，但作者验收必须是完整公开路径。测试绕过公开 CLI 直接调用内部部署函数，只证明内部或历史兼容行为。

## 2. 一份编译输入，一种可解释产物

### AD-01：标准 MSBuild 是唯一正式工程构建后端

2026-09-10 [r5 构建职责审查](../reviews/code/2026/20260910-0004-sdk-msbuild-architecture.md)调整之前“IDE 向自有 CLI/BuildPlan 靠拢”的决定。统一 CLI、IDE、CI 的目标保留，普通工程解释、恢复与 Csc 编译交给标准工具链；DTMAPI 保留游戏引用、诊断、实际产物和交付验证。具体构建边界由 [AB-01–09](platform-sdk-build.md)拥有。

0.7.0 在 PN-041 一次贯通标准工程、普通库/生成器、CLI/实际 IDE/CI、pack/Doctor、实际内部输入转换与 Mono，再首次公开 SDK。用户确认此前 SDK 未发布：不为历史 schema/客户端建立公共迁移产品，现有 Mod/Runtime 契约独立保留。r5 是内部已验旧实现，计划不冒充切换。

新集成只消费冻结 API/BCL/contract，不执行历史 props 的构建策略，不改其原字节。作者编译选项、源码/资源和工程图只在标准工程声明；内部构建结果记录实际求值与输出，不再成为第二份编译权威。SDK160/必需游戏诊断、Native/依赖/符号和准确封包继续成立，不因换后端弱化。

默认作者包携完整标准 .NET SDK 和基础离线输入，准确工具链随 SDK 发行修订；基础 Strict 无需游戏/预装 SDK，扩展包的离线条件按实际依赖说明。构建可信项目会执行作者 targets/生成器；Doctor 检查包保持非执行。SDK 仍是独立作者工具，不进入玩家安装包。

### AD-02：Debug 是真实可观察能力

SDK 提供明确 Debug/Release 输入。Debug 配置以定位作者行为为目的；Release 以可复现分发为目的。两者都必须发出游戏兼容目标框架和正确程序集引用；Debug 不能偷偷引用 host .NET 运行时。

符号规则：

- 构建生成与 DLL 同一次 emit 的符号；开发安装可携带匹配符号，正式分发可选独立 symbols artifact，不强制所有玩家下载源代码。
- 用 DLL 与符号 identity 绑定，错误符号被拒绝或明确标 unavailable；不从任意目录挑同名 PDB。
- 规范化相对源码路径，并验证用户机器路径不会意外写入公开包；包含源码的 symbol bundle 是明确选项。
- 先在实际 Doloc Town shipping Mono 验证 Portable PDB 的堆栈行号和调试器能力。格式转换只有技术证据要求时才增加。
- `源码位置可定位`、`结构化追踪可用`、`IDE 断点可用`是三个独立验收项。生成 PDB 或 VS/Rider 能打开工程不能证明断点可用。

若游戏没有开放兼容的 Mono debugger，必须将断点能力记录为技术限制，并交付可用的源码行、owner 日志、命令/状态快照和错误复现流程。不能为通过测试伪造 debugger attached；不能自动修改玩家游戏可执行文件。若唯一可行方案是独立开发者运行环境，先完成有界技术验证，再在对应架构节点决定是否纳入产品。

## 3. 本地运行、来源与状态

### AD-03：一个官方 Local 安装事务，磁盘与运行状态分开

开发安装使用游戏认可的官方 Local MODS 来源。目录定位来自现有本地设置/环境/原生事实；不恢复历史 `<game>/Mods` 作为新开发来源，不写 Workshop 订阅目录，不自动替用户启用 Mod。

安装、更新、撤回与恢复共用已存在的事务/库存/receipt 能力，按新官方路径补齐 authority；不为每个命令建立新的事务系统。包外 journal 保存 SDK 拥有的安装事实；config、save-bound data 和诊断不作为可替换包内容。

状态至少区分：准备的 artifact、磁盘上安装的 package、游戏官方启用状态、Runtime 选择来源、程序集实际加载版本/指纹、需要重启。CLI report 不能用成功写盘代表加载成功。作者同时订阅正式版和安装开发版时，报告准确说明当前来源与冲突，不能偷偷改变官方优先级或 Steam 订阅。

代码包在游戏运行时不替换已加载 DLL。更新后必须重启，以实际加载指纹证明新代码生效。获准的纯内容 reload 按对应领域契约执行；不知道语义的资源、静态缓存或原生 JSON 一律不能由 SDK 通用 watcher 猜测热重载。

包库存不符、外部文件混入、身份错误或 journal 失配时保留现场并给出 recover/人工修复指引；工具不能自行“收养”未知文件。已支持的旧部署恢复路径继续受历史契约验证，不能被误认为当前官方 Local 路径测试。

## 4. 作者诊断与测试

### AD-04：复用现有 Doctor、Runtime 状态与日志

不创建第二个诊断服务。Doctor 继续负责离线包、引用、安装状态检查；Core 负责实际运行状态、owner、依赖与生命周期；GameBridge 提供本游戏的版本、主线程、native owner/hook 可用性事实。SDK 通过已协商的作者会话读取公开支持的状态，不读取任意游戏内存。

一个作者应能从报告回答：

1. 我编译的 API target 和当前 Runtime 是否兼容，实际使用了哪个 SDK/引用载荷？
2. 游戏现在加载哪个来源、哪个包和 DLL，它是否等于我刚构建的文件？
3. 是官方未启用、依赖不满足、入口失败、生命周期尚未到、native 适配失败，还是只能重启？
4. 错误属于哪个 Mod/操作，哪些源文件行和输入能复现，下一步该怎么修？

问题码和修复语义应在 CLI/Doctor/Runtime 间一致。日志消息可以改进，但机器报告不得把本地化文本当错误分类。网络未连通、Runtime 未启动、会话超时和确认不兼容必须区分，不能根据“无响应”猜测需要升级。

支持导出复用当前报告机制，提供内容清单和有界输出，默认不包含存档、凭据、全部配置或任意目录。原始日志可能包含作者写入的私人内容，工具应在公开支持导出中提示/预览并处理可识别路径与 session secret；无需把每次本地诊断变成审批流程。没有自动上传和遥测；将来建设服务时另设可见选择。

### AD-05：按被证明的能力划分测试

| 层级 | 执行者拿到什么 | 证明什么 | 不能替代什么 |
| --- | --- | --- | --- |
| 纯逻辑 | 契约 DTO、小型 fake、作者逻辑 | 算法、序列化、schema、错误分支 | Unity 生命周期、真实 Hook 和保存 |
| 工具集成 | 完整 SDK artifact、外部作者工程、真实 CLI 子进程 | 创建/编译/打包/诊断/事务和无隐式仓库依赖 | Mono 加载、官方启用和实际游戏行为 |
| Core 集成 | 真实 Host/loader/owned helper 与临时 fixture | 会话、加载事务、owner cleanup、依赖冲突 | GameBridge hook 命中和 UI/保存效果 |
| Mono/游戏 | 与目标玩家相同的候选 Runtime、SDK 产物、实际游戏 | 类型绑定、主线程、输入/UI/生命周期、内容传播、正常退出 | 发布渠道已同步或所有平台已支持 |
| 用户交付 | 固定候选包、清洁用户环境、官方来源 | 安装、更新、故障诊断、重启、状态保留 | 长期向后兼容，需下一版本再验证 |

M1 从一个仅使用现有 API 的仓库外 Mod 开始，包含日志、配置和一个可见事件/输入行为；每个新域再增加一个最小的外部样例。没有 `DTMAPI.*` 白名单 ID、私有 friend 引用、仓库路径或维护者手工补 DLL。

作者 test kit 是小型契约测试工具和场景 recipe，不模拟整个 Doloc Town。真实游戏 runner 复用已有 runtime lock、fixture、报告和 smoke 规则；默认 NoNativeSave，保存/迁移按 PROJECT 选择已授权专用槽或必要隔离。已有日志可证明行为时不强制装 QA/HookProbe；缺少具体原生事实才做最小观测。框架帮助作者识别哪些测试必须进入游戏，而不是让 mock PASS 冒充产品行为。

## 5. SDK target、依赖与跨 Mod 工程

### AD-06：target 是可消费契约，不是 Runtime 版本别名

Runtime release、assembly compatibility identity、SDK tool version、API target、session protocol 和 Mod version 分开。SDK target catalog 是已支持组合的机器来源；Public API matrix 拥有单个 API 的稳定性和证据。新 helper 编译进 Runtime 以后，还必须进入 SDK 载荷、模板和样例才能由第三方采用。

阶段内部 target 与公开首发可以不同。M2 独立候选不以反射为验收前提；用户确定的公开首发须到 M3，届时完整 target 包含已证明反射和开放生态。具体版本由[路线](../planning/platform-next/roadmap.md#可发布版本)拥有。不修改原冻结载荷以塞入新功能，不因产品标题用了某版本就声称该 API target 已发布。

内部固定快照保留原字节/recipe 供核对，不因此永久占用公共版本号或产生历史 SDK 支持窗口。坐标改变时保留原快照、创建明确新候选并验受影响组合，不让同一标识随机指向不同字节。历史工具只在具体调查需要时重放，首发不要求重建全部内部工程。现有 Mod 的实际引用/reader 保持；PN-036 不追认内部候选长期支持。

SDK 在构建前验证选择的 target、能力和包最低 Runtime，Runtime/Doctor 在加载/诊断时验证自身职责。未知或未就绪 target 在工具中被明确拒绝；旧 schema/package 的已知恢复路径保持兼容，不扩大为对所有未知组合的静默接受。

### AD-07：依赖必须在载入前可解释

M3 的作者工程区分三类引用：平台契约、Mod 间共享契约、产品私有纯 managed 库；Advanced 本地原生引用另行记录。编译引用不等于允许分发，打包必须验证运行时闭包和许可证文件。字段、旧 reader 分流、SemVer、预加载冲突和构建输入细则由[包契约 P01–P07](platform-package-contracts.md)拥有。

共享契约以真实 assembly/type identity 为准，先支持显式共同 contract DLL。两个作者复制同名接口不构成同一个契约；暂不引入结构代理来隐藏类型不一致。私有 DLL 也不能假设 Unity Mono 单 AppDomain 能隔离任意同名不同版本库。

规范要求：

- 包声明/解析结果列出实际依赖 identity、内容 hash、角色及分发来源；SDK/Doctor/Runtime 复用共同校验逻辑，阶段不同不能给相反解释。
- 同 identity 不同字节冲突必须在实际执行前诊断；不能按目录枚举顺序任选一个。
- optional Mod 缺失时可降级；required Mod、契约或库不满足时阻止依赖它的代码执行，其他独立 Mod 可继续。
- Shared contract 的升级策略与 Mod 版本分开，跨 Mod API 的可用时机遵从生命周期。旧 provider/consumer 组合进入实际 Mono 验收。
- Advanced 引用只从作者明确的合法游戏环境解析，包不带游戏 DLL/Unity 原始资产；build provenance 说明适配依据，不伪装成维护者签名或永久游戏兼容保证。

CI 先有基础离线 Strict recipe，后有显式恢复依赖的扩展 recipe。有实际游戏安装和授权 fixture 的 runner 才运行 native/Mono tests；公开 CI artifact 不包含官方二进制、存档或用户凭据。

## 6. 发布、升级、兼容和支持

### AD-08：先完整离线交付，再考虑自有在线服务

当前产品方向继续使用官方 Workshop 分发；成熟平台不以 DTMAPI 自建账号、中央 registry 或自动上传服务为前提。先提供确定性 publish staging、元数据校验、依赖/最低版本检查、许可证/符号产物、手动官方发布指南和用户侧诊断。之后的自动上传只是可选 adapter，凭据存储与提交必须有独立明确设计。

包可构建、可交付、已发布、已订阅、已安装、已启用、已加载、行为通过分别记录。既有 Catalog/current subscription manifest/release Update 继续拥有第一方发布事实；第三方作者自助路径不能要求维护者向第一方 Catalog 加一行才能产包。

发布候选至少包含 Runtime 与 SDK 兼容矩阵、包内容检查、仓库外作者样例、实际 Mono 行为、清洁用户安装/更新/恢复、支持文档命令验证。对涉及保存/内容/UI 的域额外执行该域验收；通用 build PASS 不能代替。

### AD-09：兼容范围按承诺种类拆开

| 承诺 | 默认方向 | 验收 |
| --- | --- | --- |
| Stable Public API | 同一稳定 major 保持源与二进制兼容；新增服务采用扩展入口，旧 helper implementer/consumer 继续运行 | 固定旧编译 DLL 的真实方法调用和 Mono 加载；不只比较符号表 |
| Experimental/候选 API | 有显式稳定性标记、变更说明和迁移路径；不据此承诺永久冻结 | SDK 诊断和样例迁移，必要时 feature detection |
| 作者工程/schema | 首次 SDK 只支持一个标准输入，转换当前内部工程；实际公开后才承担版本间兼容/迁移 | 0.7.0 验新作者与现用内部输入；未来公开两代后验真实迁移，不造旧 SDK 用户 |
| Session/工具报告 | 版本协商、能力缺失/未知字段和实际状态恢复 | 新 SDK/受测 Host 与不兼容负例；未发布旧客户端不构成首发承诺 |
| 游戏 native 适配 | 指明已验证 build/范围，失败可定位；不把历史成功推广到未来游戏 | 当前实际游戏与一次版本漂移回归，Hook/state owner 再核对 |
| Config/save 数据 | 明确 schema 和迁移，保存数据继续遵循原生提交与回滚 | 升级、重复执行、失败恢复、未保存退出、旧数据保留 |
| OS/分发 | 仅承诺验收过的作者宿主与玩家 Runtime 组合 | 实际路径/大小写/IPC/库绑定/安装和退出测试 |

“同 major”是稳定版本的目标规则，不把当前所有 pre-1.0 或历史 Experimental 面强行追认 Stable。正式稳定版前，在架构复盘中确定具体支持窗口和退役期限；在那之前不得承诺永久保存所有历史 SDK target，也不得删除仍受支持的兼容路径。

维护机制从第一版样例开始累积：冻结的旧 consumer DLL、项目输入、必要数据 fixture、支持组合和实际运行结果。弃用必须有替代路径、编译/Doctor 提示、迁移实例和公布期限；内部重构不借此删除公共 ABI。

作者沉默时仍按明确的兼容承诺演进，具体执行如下：

1. 在既有 Public API matrix 和对应发布/实施记录标明已发布范围、稳定性、替代面，以及源码/二进制/行为/数据的影响。消费者状态区分“已知使用”“检查范围内未发现”“未知”；不建立要求所有作者登记的新平台门槛。
2. 内部可先换新实现，旧入口保留必要的薄适配层。仅在行为等价时转发；无法等价的变化必须说明差异和数据风险。Frozen 或无人回复不等于公共入口可删除。
3. 提供可运行迁移示例、非 error 的 Obsolete 编译提示，以及 owner/feature 去重的运行诊断与 Doctor 解释。只编译新源码看不到旧 DLL 风险，因此同时保留旧 consumer/implementer 调用语料。
4. 首次正式弃用时公告最早移除版本与日期，两者都满足才到移除候选；在预览候选验证旧包失配的诊断、替代路线和回退。没有作者回复不无限延长已公告窗口，但未知使用量也不成为提前移除的证据。
5. 移除前复核支持范围内已知消费者与未知风险、兼容层成本、替代能力和发行恢复。旧内部实现可先退役，不把整个旧系统与薄 ABI 层绑在一起；数据迁移/存档格式另有独立恢复要求。

用户已选择 0.8.0 开始正式清退旧接口；PN-033.a 在 0.7.0 前准备，b 在 0.7 系列提供逐族公告/迁移/移除预览，c 在 0.8 起执行满足条件的集合。R-Compat 不等整个 M6 完成，R6 另外决定未来稳定核心的长期支持成本。首次公开公告需给出具体最早移除版本与日期；规划日期不是已经公告的日期。

首批面向已退役/禁用实现、Frozen 玩法桥接与无 native host 的旧外壳，准确清单由 API matrix 及 retained MemberRef 语料确定。源实现删过不代表 ABI 壳删过；新产品功能也未必提供旧 API 的可编程替代。仍需的薄层、稳定 IDtmHelper/Entry ABI、存档兼容 reader 和所有旧 target 的可用子集不自动随 0.8 消失。每族明确“替代”或“能力停止提供”，失败旧包有预加载诊断及回退。

研究中的“两个周期/90 天”等只是可讨论示例，当前不据此追溯删除或宣布固定长期期限。作者未回复不无限延期；日期未到、已承诺支持或保存恢复条件未齐的家族延期至后续 0.8.X，不拖住其他已齐家族。只有实际形成新的支持成本/长期承诺冲突时才交给用户决定。

### AD-10：更新通知不控制本地运行事实

当前 UpdateKeys 的存在不表示更新服务已实现。将来更新/兼容通知使用可选 provider、超时、缓存和离线降级；本地实际包、Runtime 和游戏信息始终可诊断。远程“有更新”“已知不兼容”“维护者停止支持”分开，不能凭未知/过期远程数据自动删文件、替换 DLL 或执行下载。

支持流程先形成离线可用的 issue 模板和一键报告：作者附包版本、来源、最小复现、owner 错误和相关场景结果；支持人员无需用户全目录或存档就能处理普通加载问题。只有保存/内容损坏等特定调查才按专门协议收集对应数据。

## 7. 正常作者工程的选择权

### AD-11：普通工程只声明一次，迁移不冒充零行为变化

输入归属及 author schema4 由 [AB-02](platform-sdk-build.md#ab-02每种输入只声明一次)拥有：编译、引用、资源、生成与条件全部在标准工程；manifest 拥有 Mod 身份，author 描述只保留游戏/交付输入。普通库不需要 Mod 身份或 API target；构建机工具不受游戏 DLL TFM 限制。

旧 SDK 未发布，按 [AB-08](platform-sdk-build.md#ab-08旧工程旧包与回退)只转换实际使用的内部模板/工程，保留有效输入和行为对照，不建通用 migrate-build 或历史工具重建矩阵。框架常量/EditorConfig/targets 的新标准语义如实解释；已发布 Mod 原包兼容独立验证。旧 PN-039 只是当时子集证据。

### AD-12：先选择资产，再判断是否可执行

标准 NuGet 拥有恢复与资产选择，DTMAPI 对实际交付闭包执行 PE、身份、许可和宿主检查，规则见 [AB-05](platform-sdk-build.md#ab-05标准恢复区分三种资产)。build-time、compile-time、runtime 资产分开；不同字节 ref/lib 在 PN-041 内接通，生成器/targets 不因为参与构建就进入玩家包。PN-040.a 的历史结果保留，不继续扩充自有 resolver。

较低 TFM/facade、RID/native、卫星资源等运行支持不是标准构建自动附送的承诺。PN-040.b 只保留未被迁移吸收的运行兼容范围，先证明真实 Mono/BCL/旧 reader，再扩大游戏加载规则；不得伪造 TFM 或删除宿主检查。日常标准 restore 的网络行为与明确离线/发布锁定模式必须准确说明。

M4 原生数据/内容实验与本层无直接技术依赖；当前执行优先级按用户要求先完成 0.7.0 SDK 架构收口。之后继续 SaveData、GameContent、Host/Pack，不将低 TFM/所有 NuGet 或更多 IDE 支持变成整个 M4 的前置。

## 8. 本领域的架构复盘点

- M1 实际外部作者循环完成后，复核构建/安装/来源/调试承诺，处理真实 Mono 反证，再进入批量公共服务扩展。
- M3 自助 Advanced 和共享 DLL 首个真实 prototype 后，复核本地原生引用面、Mono identity/依赖冲突和跨 Mod 契约；此节点不重做无关安装或文档设计。
- R-Generic：按 P08 复核格式与三端验证/Mono，不重开旧 helper ABI。R-AuthorBuild 在 PN-041 的标准构建、准确交付、最终产品三处有界核对并连续推进；R-Assets 只审后续运行资产兼容，不重新选择后端。
- 首次带 config/save/content schema 的版本升级后，复核长期迁移和作者支持操作，不能只验新建项目。
- 稳定发布承诺前，确认支持窗口、弃用期限、已承诺平台组合与维护资源。若要自建在线服务或独立 debugger 运行环境，也在相应节点作产品决策。

其余内部选择由执行者按本页实施；只有新的事实推翻已接受语义或形成新的长期用户承诺时，重开对应决策。
