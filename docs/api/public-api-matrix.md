# DTMAPI Public API Stability Matrix

Status date: 2026-09-10

This matrix is the public API stability contract. It is intentionally stricter than the smoke-evidence ledger: a smoke run can prove that a code path executed, but it does not by itself make an API stable for ordinary mods.

## Status Vocabulary

| Status | Meaning | Compatibility Promise |
| --- | --- | --- |
| Stable | Public contract is DTMAPI-owned or has proven native owner coverage. Breaking changes require migration notes, compatibility handling, and a new update record. | Ordinary mods may depend on it. |
| StableCandidate | Contract shape is likely correct, but it still lacks one or more promotion gates such as two real mods, manual QA, or regression matrix coverage. | Ordinary mods may experiment, but should expect final polish changes. |
| Experimental | API is usable for test mods or carefully scoped real mods, but native ownership, lifecycle, conflict behavior, or failure modes are not fully proven. | Ordinary mods should treat it as version-sensitive. |
| Diagnostic | Debug, smoke, report, console, or developer-support surface. It may call powerful native paths, but it is not a stable gameplay API. | Ordinary gameplay mods should not depend on it. |
| Proposed | Design direction or desired API surface with no current stable implementation guarantee. | Do not depend on it. |
| Failed | Existing implementation or evidence is known insufficient or contradicted by manual QA. | Do not use as completion evidence or stable API proof. |
| Disabled | Public shape is retained only to keep old binaries loadable; the provider fails closed and performs no gameplay work. | Do not adopt it. Existing consumers must migrate; physical removal still requires the documented breaking-version warning and scan gates. |
| Retired | Public surface or hook route existed in an experimental branch but was intentionally removed from active runtime/API code. | Do not depend on it; treat old evidence as archive/research only. |

`Blocked` is a qualifier, not a status. A row may be `Experimental` and explicitly blocked for native runtime creation until its GameBridge adapter is proven.

Source metadata keeps two independent dimensions. `DtmApiStatusAttribute` describes stability; the additive `DtmApiDispositionAttribute` describes whether a surface is open for adoption, frozen for compatibility, diagnostic-only, DTMAPI-internal, or disabled. Declarations without disposition metadata are `Open` by default. `Frozen` retains the existing ABI but rejects new capability work and must carry a non-error `[Obsolete(..., false)]` source warning; it does not turn an Experimental API into Stable or start a promised removal release by itself.

## Stable Promotion Criteria

An API may move to `Stable` only after all relevant gates are satisfied:

1. It is backed by a clear DTMAPI owner or a reviewed Doloc Town native responsibility owner.
2. It exposes stable DTMAPI contracts and does not expose raw Unity, Harmony, BepInEx, or copied decompiled game types.
3. At least two real mods, not only a smoke helper, use the API successfully.
4. Game evidence proves the API in the appropriate real gameplay path, usually the third local save unless a task states otherwise.
5. Visual, UI, input, camera, save/load, lifecycle, machine, vehicle, or other player-visible APIs have manual QA or screenshot/video evidence that covers the actual user-facing failure mode.
6. The debug regression matrix has a row for the API's main success path and high-risk failure path.
7. Clean exit evidence exists when the API participates in runtime/gameplay behavior: no leftover `DolocTown.exe` and no Steam waiting-for-exit regression.
8. Known failures, rejected hypotheses, and rollback notes are recorded in the relevant debug, review, hook-map, update, or API contract document.

Static screenshot smoke is allowed as supporting visual evidence, but it is not completion evidence for a visual/UI/camera API unless manual QA or an equivalent targeted visual review covers the same failure mode.

## Native Owner Domain Library Boundary

Future API domains that are not yet represented by a public matrix row should first be checked against `docs/reviews/api/native-owner-domains/INDEX.md`. That library records native owner candidates, official Workshop content/beauty boundaries, and blocked/gap status for broad gameplay/content requests. It is not a stability contract: a report may justify a proposed DTO or GameBridge adapter, but it does not promote an API to `Stable` or `StableCandidate` without the promotion criteria above.

## Internal Product UI Boundary

The title-page DTMAPI Manager UI is an internal product UI over existing Diagnostic and Experimental runtime data. `DtmManagerViewModel`, Manager row formatters, Manager report/export state, and Status Copy Summary are not `DTMAPI.Abstractions` public mod APIs. Their presence in the first-party Bootstrap assembly does not promote `IDtmDiagnosticsApi`, `IUiHelper`, CameraView, FishingAutomation, SaveSlots, or any GameBridge feature API to `Stable` or `StableCandidate`.

Manager UI smoke evidence may prove that support rows, summary text, and report export are visible in the title settings UI. It must not be cited by itself as native-owner proof for gameplay, save/load, camera, fishing, vehicle, equipment, machine, or content APIs.

## Current Compatibility Decisions

### 0.7 candidate migration and removal preparation

This is preparation owned by [PN-033.a](../updates/2026/20260909-0016-platform-deprecation-preparation.md), not a published removal notice. Actual announcement date: **not announced**. Actual removal date: **not scheduled**. Earliest eligible breaking series: **0.8.0**, subject to the existing per-family notice, retained-binary, replacement and rollback gates. Nothing in 0.7 physically removes these interfaces, DTOs or storage readers.

| Existing family | Migration or unavailable behavior | Compatibility distinction |
| --- | --- | --- |
| Lamp | Remove the gameplay dependency; no replacement light-control API | Disabled shell stays deterministic; no Hook or light mutation |
| Custom animal/monster/attack/drone | Keep explicit blocked/unavailable handling; no public native-creation replacement | Registry/DTO ABI remains; registry acceptance is not native creation |
| ActionCompletion, ActionSpeed, FishingAutomation | Player products OneActionComplete, ActionSpeed, AutoFishing | Existing compatibility executors remain; product adoption loses programmable control through the old API |
| ItemTooltip, AnimalViewer, ChestLocatorEnhancer | Player products FishBreedingAssistant, AnimalHusbandryProgress, ChestLocatorEnhancer | No equivalent new public API; existing thin contracts remain |
| CameraZoom and CameraView | Player Zoom product; do not migrate between the two frozen APIs | Old binaries and applicable compatibility host remain; product camera behavior is separately verified |
| EquipmentSlots and SaveSlots | Player products MoreEquipmentSlots and MoreSaves | Native slots and owner data are not deleted; no new public slot API |
| MachineProduction and StrongPlantingGun | Player Mine and StrongPlantingGun products, or explicit missing-provider handling | Public shapes remain, but no runtime provider is promised; adding diagnostics does not restore a provider |
| Migrated DebugConsole diagnostic shapes | Keep the types actually used by retained/current products until their consumer scan closes | Moving execution out of GameBridge, removing an alias/provider, and deleting an interface/DTO are different changes |

Runtime warnings identify consumer owner and requested obsolete contract once per owner activation; owner cleanup releases the warning state. Doctor inspects known metadata references offline. Neither path rejects a Mod merely because its API target is old. Source/retained/local-package scans are bounded inventories and cannot establish absence of unknown third-party consumers. Existing owner configuration/global data survives package withdrawal; removing its reader requires a separate data migration decision.

- Old DebugConsole `0.3.1-dtmapi` has no remaining users according to the accepted 2026-08-30 decision; a future bounded breaking cleanup need not reopen that user-count prerequisite. This does not remove compiled interfaces or the 28 DTO/enum types still used by public `1.1.1`. Keep or internalize actual consumers before removing the old provider/UI/action path.
- ProductNative Monster/Animal UI and spawn-result policies do not promote Diagnostic APIs. Source candidates and published product bytes are separately recorded by their owning Update and Catalog; `SpawnDebugResult.SpawnedCount` remains the count of roots whose public postconditions passed.
- `IProtectedStorageApi` is a discussion name, not a declared or admitted capability. General protected-storage API work remains paused; any new proposal needs one data authority and one production adapter.
