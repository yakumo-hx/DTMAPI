# Complete Release Cost, Resume, And Code-Growth Audit

Status: recorded

Date: 2026-07-24

## Scope

This audit answers the user's questions after the eighth Advanced product task:

1. why the apparent complete Release produced many failures and consumed about
   five hours and forty-nine minutes;
2. whether checkpoint/resume actually worked;
3. what `tools/scripts/test.ps1 -Configuration Release` does;
4. why product-specific hard-coded assumptions repeatedly appeared;
5. what caused the approximately 5,500-line increase.

This is an audit-only Review. It does not change the Release runner, the eighth
product, its Update, or its acceptance state.

## Verdict

The five-hour-forty-nine-minute interval was not one complete Release run. It
combined eighth-product implementation, at least ten from-start Release
attempts visible in the streamed transcript, focused repairs, diagnostic tails,
game acceptance work, two independent code audits, and the fixes found by
those audits.

The current runner has no checkpoint or resume implementation. The later
`temp/run-eighth-release-unreached-tail.ps1` run was a non-authoritative
diagnostic tail assembled by extracting part of `test.ps1`; it cannot be joined
to an earlier partial result to create a complete-suite PASS.

The approximately 5,500-line increase was not generated by Release fixes. The
exact `d38af17a..034ea5e6` net increase is 5,596 lines, and it occurred after
the first complete Release PASS when two independent audits found real product
transaction, cold-recovery, shield, and physical-owner proof gaps.

## 1. Time And Retry Reconstruction

Historical complete Release runs normally took roughly ten to twelve minutes:

- 582.1 seconds in
  `docs/updates/2026/20260715-0019-batch4-qa-host-extraction.md`;
- 710.9 seconds in
  `docs/reviews/code/2026/20260715-0006-batch2-closure-and-batch3-predecision-review.md`;
- 725.2 seconds in
  `docs/reviews/code/2026/20260720-0003-batch5-closeout-and-batch6-phase0-acceptance-audit.md`.

The supplied streamed transcript contains at least eight explicit from-start or
restart points before the first complete PASS and two more after independent
audit changes invalidated that candidate. It also contains separate Unit
reruns, focused child-script runs, game smokes, and manually constructed tails.

The largest avoidable costs were:

- starting a complete suite before committing a candidate even though the
  Workshop provenance gate rejects dirty mandatory sources;
- performing the independent product audit only after the first complete PASS
  and game smoke;
- discovering a wrong PowerShell host after earlier stages had run;
- generating new game evidence without refreshing the evidence allowlist
  before the next expensive attempt;
- using a fail-fast serial driver, so unrelated late historical-gate drift was
  revealed one item per attempt.

The strictness of individual correctness checks is not the main problem.
Preflight order, audit order, permanent historical checks, and lack of phase
selection caused the repeated cost.

## 2. Resume Finding

`tools/scripts/test.ps1` accepts only:

- `Configuration`;
- `TestTempRoot`;
- `KeepFailedTestTemp`.

It has no `StartAt`, `Only`, `Resume`, frozen-input manifest, or phase-state
validation. It is a serial fail-fast script.

The later tail script:

- reads `tools/scripts/test.ps1` as text;
- extracts the body beginning at the product Catalog checker;
- stops before document governance;
- executes that substring;
- records only its start/end markers, HEAD, completion time, and result.

At 2026-07-24 05:52:10 +08:00 that diagnostic tail passed at
`034ea5e6cd40a5fee7708122a6640a0e41460ef2`. It proves the selected unreached
tail was green. It is not a complete Release PASS and it does not prove that
HEAD, tracked tree, configuration, toolchain, and artifacts stayed identical
across an interrupted run.

This behavior is consistent with the proportionality rule: focused failure
repair plus one diagnostic tail, followed by one clean from-start suite only
when a complete-suite acceptance is actually required. It should not be
described as checkpoint resume.

## 3. Release Purpose And Cost Shape

`tools/scripts/test.ps1 -Configuration Release` is a repository-wide
pre-release acceptance suite. It does not upload a Workshop package, launch
Doloc Town, execute real L0-L5 game ladders, or perform a long GC test.

Its serial stages include:

- building the repository and running Unit, QA Unit, and InstallDoctor tests;
- building and checking Player Doctor and temporary Runtime packages;
- evidence-retention and generated-allowlist checks;
- PowerShell syntax, path, and download-marker safety checks;
- Author SDK build, tests, and portable package checks;
- ownership, uninstall, invalid-target, upgrade, and install transactions;
- 34 Runtime upgrade transaction cases across PowerShell 7 and 5.1;
- Catalog and retained Phase 0/product gates;
- two deterministic SDK package builds for each of eight Advanced products;
- release contract, QA semantic, static GC/behavior/lifecycle, ABI, artifact,
  and document-governance checks.

This breadth is appropriate for a final integration or release candidate, but
it is disproportionate as a mandatory gate for every product extraction.

Both eighth-product admission authorities explicitly said a complete Release
was not required:

- `docs/reviews/code/2026/20260723-0009-eighth-product-more-equipment-slots-admission-review.md`;
- `docs/reviews/code/2026/20260723-0010-eighth-product-admission-runtime-weight-and-api-reuse-audit.md`.

The implementation Update later added one complete Release as a final gate:

- `docs/updates/2026/20260723-0008-more-equipment-slots-eighth-advanced-product.md`.

That was an unapproved expansion of the admitted acceptance scope. The complete
suite belongs at the final 0.5.5 integration/release boundary unless a later
bounded authority explicitly requires it sooner.

## 4. Repeated Product-Specific Hard Coding

The default suite currently mixes:

1. live product and platform invariants;
2. package, SDK, installer, and release-contract validation;
3. historical Batch 4/5/6 milestone and source-token replay.

The eighth product changed Catalog membership, component counts, Hook ownership,
and directory projections. That exposed stale copies such as:

- literal GameBridge feature counts `14` and `15`;
- an Animal gate expecting `25` Hooks owned by other products;
- an old ActionSpeed “three product” filter string;
- an old G2 `TrackedPolicySha256` source token;
- stale YConsole published-version projection;
- an assumption that every Catalog row has `codeModKind`;
- stale QA inventory paths, Hook totals, input text, and removed Smoke
  parameters.

Exact ABI members, Workshop identifiers, native targets, and Harmony owners can
legitimately be fixed values. Global product totals, internal source strings,
and another product's implementation tokens should be derived from the Catalog
or replaced by a small live invariant. Full historical replay should not remain
in the default product-integration path.

## Recommended Corrections

Before the next complete suite:

1. restore the eighth-product Update to its admitted focused acceptance scope;
2. add a cheap preflight for committed/clean candidate provenance, supported
   PowerShell host, generated allowlist, Catalog, and document governance;
3. add lightweight non-authoritative `-Only` and `-StartAt` phase selection,
   explicitly labelled diagnostic rather than resumable acceptance;
4. report per-phase elapsed time and the exact failing phase;
5. move full historical Batch replay outside the default product-integration
   suite, retaining only current regressible invariants;
6. run independent product/code audit before final game evidence and any final
   complete suite;
7. reserve one clean from-start complete Release for the frozen 0.5.5
   integration candidate.

Do not add checkpoint receipts, cached-pass authority, or a second assurance
system. A later formal resume feature would have to prove unchanged HEAD,
tracked tree, configuration, toolchain, and required artifacts; the lightweight
diagnostic phase selector does not need or claim that authority.
