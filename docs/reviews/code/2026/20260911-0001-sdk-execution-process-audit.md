## High 的具体不足及已有修复

1. **跨组件闭环漏检。** V2 元数据在 SDK/Core/Doctor 通过，最终 owner 分支仍只接受 V1，直到实机拒绝；原任务随后补齐 classifier→supervision→loader→Entry→close。见 [0003](../../../updates/2026/20260910-0003-sdk-delegates-native-generics.md)。问题是局部通过被用于判断整条链，解决办法是选择完整路径的代表用例。
2. **实际旧输入进入得晚。** r5 拒绝带旧 `dtmapi-package.json` 的 16 个既有包，0.6.1 对照接受；由 [Review 0006](20260910-0006-existing-package-marker-collision.md)定位并修成 r6。既定 PN-042.a 已要求旧包基线，执行顺序没有充分利用它。
3. **构建“标准支持”反例不足。** D6 验证了方法匹配，漏了字段静态/实例与六类指令；常规子目录工程也未贯通 validate/build/pack。这是实现和覆盖缺口，独立审查有实际价值；增加同一健康全套的运行次数不能替代这些反例。
4. **工具调用和环境复用不稳。** 一次 focus 漏 `--focus` 被已有解析器立即拒绝；IDE 再启动遗漏受控 SDK 环境；探针出现输出碰撞、旧目录不存在等。这些是可避免的小失误，应复用本任务已纠正的命令和路径。未知 focus 的快速拒绝已经存在，无须再实现一层。

High 能完成复杂实现、根据失败修复并给出最终证据，但本次执行在验证排序、边界覆盖和工具轮次上有改进空间。没有证据表明把 High 全部换成 Max 就能消除这些问题。“Max 设计、High 执行”仍可使用；设计交接应提供最关键的实际输入、反例、终点与外部限制，而不是更多重复文档。本次只修流程，不改变用户模型选择。
