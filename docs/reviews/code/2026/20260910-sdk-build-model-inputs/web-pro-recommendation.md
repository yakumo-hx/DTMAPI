**我的建议是：保留并加强 DTMAPI SDK，但把它定位为“面向多洛可小镇的开发与交付工具”，而不是“规定作者如何编写 C# 工程的系统”。**

具体说，就是：

> **普通工程怎么组织，由作者和标准工具链决定；游戏需要哪些引用、最终交付什么、能否被 DTMAPI 正确加载，由 SDK 和运行时共同验证。**

这比“尽量少限制”更准确。你不需要在“封闭但可靠”和“开放但什么都不检查”之间二选一。真正应该改变的是：**哪些事情属于作者自由，哪些属于平台契约，以及检查发生在哪里。**

我也修正之前的建议：统一 CLI、IDE 和 CI 的方向没有问题，但让它们长期围绕自有工程解释器统一，并不是最合适的基础。现在应该纠正这一层，而不是继续为每一种普通 C# 功能增加专用支持。

这次我查看了你上传 SDK 的模板、冻结 props、原生引用说明、项目与依赖规则。**没有运行 Windows CLI 或重新执行你贴出的编译实验**；下面对实验的判断以你提供的结果为依据，对包内现状则注明了对应证据。当前文档已经明确开放陌生作者的 Advanced，并说明 SDK160 不再按注释、字符串中的名字误判，这些旧问题不应继续作为本版的批评依据。〔S1〕

## 一、SDK 到底有什么用：减少作者的重复劳动，而不是代替作者做所有决定

先把四个容易混在一起的东西分开：

| 层次            | 它主要解决什么                       | DTMAPI 中的对应事物                 |
| ------------- | ----------------------------- | ----------------------------- |
| **运行时框架**     | 游戏启动后，怎样加载 Mod、发送事件、管理注册与生命周期 | 游戏里的 DTMAPI、GameBridge 等      |
| **公共 API**    | 作者可以调用哪些接口，各自承诺什么             | `DTMAPI.Abstractions` 及相关契约   |
| **作者 SDK**    | 怎样创建工程、引用 API、生成交付包、安装测试和定位错误 | 模板、引用准备、构建扩展、CLI、Doctor       |
| **通用 C# 工具链** | 怎样解释工程、还原依赖、运行生成器并编译代码        | .NET SDK、MSBuild、NuGet、Roslyn |

标准 .NET 项目 SDK 本身就是由构建配置、目标和任务等组成的工具集合；它负责组织普通工程的构建过程。DTMAPI 可以扩展它，并不需要替换它。([微软学习][1])

**SDK 的价值，不在于作者离开它就寸步难行，而在于使用它之后，少写配置、少踩坑、少做重复操作。**

例如，作者想做你之前讨论的音游 Mod：

* 谱面解析、判定算法和得分计算，可以放在普通 C# 库中。
* Unity 界面、输入以及游戏内入口，放在 Mod 工程中。
* 谱面转换工具、测试工程，可以独立开发，不进入游戏包。

DTMAPI SDK 应该帮助他连接这些部分，并验证最终进入游戏的内容；**不应该要求谱面解析库也必须具有 Mod 身份、接受专用目录结构，或者只能使用框架预先认识的构建方式。**

还有一条边界很重要：

**SDK 不能代替运行时 API。** SDK 可以提供一个“创建菜单”的示例和诊断，但游戏里究竟能不能创建菜单、什么时候可以创建、关闭后如何释放，仍然是公共 API 与运行时的责任。不要把 SDK 做得越来越大，来掩盖运行时能力本身的缺口。

## 二、我建议的长期架构：一个标准构建过程，外加游戏专用能力

SMAPI 值得借鉴的是职责分工，而不是“它完全没有限制”。它的 ModBuildConfig 提供游戏引用、调试配置、部署、ZIP 和代码提示；实际 `smapi.targets` 也是向普通构建过程补充引用、验证和部署任务，而不是自行解释整个 C# 工程。

对 DTMAPI，我建议采用下面的分工。

### 1. MSBuild 是工程解释的唯一权威

以下内容全部交给标准工具链：

**源码集合、条件编译、项目引用、NuGet 引用、资源、代码分析器、源码生成器、Debug/Release、自定义构建步骤、`Directory.Build.props/targets`。**

这里的“交给”必须是真正交给，而不是：

> 先让 MSBuild 算出一部分信息，再由 DTMAPI 重新组装另一套编译参数，调用自己的编译流程。

后一种方式仍然会产生两套语义。

DTMAPI 可以读取标准构建的有效属性、引用和输出，形成报告并执行检查；但这些应该是**标准构建产生的事实**，不能再变成另一份由作者手写、与 csproj 竞争的编译配置。

### 2. DTMAPI 负责游戏专用的构建扩展

建议保留的能力包括：

| SDK 能力        | 应该负责到什么程度                              |
| ------------- | -------------------------------------- |
| **API 与引用准备** | 选择 API 目标，提供正确的编译引用；准备本机 Native 编译视图   |
| **游戏专用诊断**    | 提示 API 误用、声明不一致、已知宿主不兼容，而不是重定义普通 C# 语法 |
| **产物检查**      | 检查实际 DLL、直接与间接依赖、宿主程序集身份和 Native 契约    |
| **打包**        | 生成官方需要的目录、清单和元数据，排除不能分发的文件             |
| **安装与测试连接**   | 在明确授权和正确目录中安装，确认磁盘产物与进程实际加载情况          |
| **问题诊断**      | 给出可执行的错误解释、符号匹配、日志与兼容性信息               |

这些可以复用现有库和 CLI，不意味着要新建六个工程或六套基础设施。

### 3. CLI 是便利入口，不是另一种工程语言

作者仍然可以使用：

```text
dtmapi-author build
dtmapi-author pack
```

但其内部关系应当是：

```text
CLI / IDE / CI
    → 标准 MSBuild 工程
    → DTMAPI 引用准备、诊断与产物检查
    → DTMAPI 打包
```

**只能单向调用，不应出现：**

```text
CLI build → MSBuild Build → CLI build → …
```

构建任务需要调用现有工具时，可以调用不再发起编译的“底层操作”，例如引用生成、程序集检查或打包，而不是再次调用完整的 `build`。

微软提供的 `BeforeTargets`、`AfterTargets` 和依赖目标扩展机制，正是用于把这些专用任务接入标准过程。新实现没有必要继续覆盖整个 `Build`、`Rebuild` 和 `Restore`。([微软学习][2])

## 三、“不过多限制”应该怎样落实：把错误、风险和建议分开

我建议为每一条 SDK 规则回答一个问题：

> **违反它之后，究竟会导致什么具体问题？**

如果回答只是“我们的解析器目前没支持”“维护者习惯这样写”“这样方便内部治理”，它就不应该被包装成游戏运行的必然要求。

可以按下面的方式处理：

| 情况                                 | 合适的处理                                          |
| ---------------------------------- | ---------------------------------------------- |
| 必需入口不存在、必需依赖缺失、包路径越界、混入禁止分发的宿主 DLL | **硬性错误**：不能生成有效交付包或不能加载                        |
| 作者声明 Strict，却实际引用了原生游戏程序集          | **契约错误**：说明如何显式改为 Advanced，不需要申请作者准入           |
| 当前 Native/依赖格式无法表达某种产物             | **明确“不支持此产物模型”**：不能伪装成已验证，也不能说它一定是恶意或 Mono 不支持 |
| 新游戏版本尚未经过测试，但当前必需签名检查通过            | **未验证提示**：是否允许加载沿用明确的运行时策略                     |
| 可能泄漏注册、可能在不合适的生命周期操作对象             | **代码诊断**：能证明的错误准确报错，启发式判断通常先警告                 |
| 命名、目录偏好、是否拆类、作者选择的普通构建方式           | **默认值、示例或可关闭建议**，一般不应成为平台硬门槛                   |

**“当前工具不能验证”与“游戏不可能运行”，必须使用不同的错误信息。**

同样，“作者自由”不等于给一个万能的 `--force` 来跳过完整性检查。遇到当前契约无法描述的 Native 用法，应当扩展契约、明确限制或提供受支持的替代做法，不能通过关闭验证把它伪装成可靠交付。

### Strict / Advanced 不应成为两套编程制度

我建议让这两个类别只表达一件事：

**这个 Mod 是否依赖游戏原生实现，以及相应的兼容性责任。**

不应该让它们同时决定作者能否使用生成器、NuGet、普通辅助库、自定义常量或标准工程属性。

也就是说：

> **Strict 与 Advanced 可以有不同的引用和运行契约，但应该使用同一套正常的 C# 工程能力。**

你当前包已经开放了 Advanced 的作者 ID，这个方向应保留；不要在迁移中重新变成依靠第一方名单的特殊通道。〔S5〕

### 硬性检查应尽早提示，但最终仍以真实产物为准

“根据产物契约检查”不等于让作者直到打包最后一刻才知道问题。

正确方式是：IDE 和构建阶段尽早提示，打包与运行时再检查关键条件。**早期诊断负责减少试错，最终验证负责防止遗漏与绕过。**

至于建议性诊断，应当尽量使用正常的 Roslyn 诊断编号，让作者通过 `.editorconfig` 等标准方式调整严重程度。SMAPI 的构建包就提供可抑制的代码警告；微软也有标准的诊断严重程度配置机制。 ([微软学习][3])

## 四、这份 SDK 中，哪些限制值得撤掉，哪些应该继续保留

### 1. 最值得撤掉的是“同一件事声明两遍”

当前 `PROJECTS-AND-RESTORE.md` 明确要求某些项目引用、资源、生成源码和 PackageReference 与 JSON 声明匹配；还限制了继承的构建配置、项目图规模及资源大小等。〔S3〕

在标准 MSBuild 架构下，我建议：

**编译相关的信息，留在标准工程中；DTMAPI 专用的信息，才留在 DTMAPI 配置中。**

例如：

| 信息                        | 建议的权威来源                          |
| ------------------------- | -------------------------------- |
| 源码、常量、项目引用、资源、分析器、生成器     | csproj、标准 props/targets          |
| NuGet 依赖与解析结果             | PackageReference、NuGet 配置、标准还原结果 |
| Mod ID、Mod 依赖、最低 Runtime  | 现有 manifest 权威                   |
| 本机游戏路径、Native 动态必需成员、发布说明 | DTMAPI 专用配置                      |
| DLL 摘要、实际依赖、最终包清单         | SDK 从构建输出自动生成                    |

**不要要求作者在 JSON 中再列一次已经写进 csproj 的项目引用和资源。**

像“最多 32 个项目”“资源不能超过 16 MiB”这类当前工具边界，也不应该自动成为长期 Mod 协议。确实需要防止异常资源占用时，可以设置可解释、可配置的工具预算；但对于一个包含音乐和动画的小游戏，资源大一些本身并不能证明错误。

相反，**包内路径越界、覆盖不属于自己的文件、把游戏 DLL 当作自带依赖**，仍然值得严格限制。它们与普通工程自由不是同一问题。

### 2. 普通辅助库应该保持普通

当前包已经支持没有 Mod manifest 的普通辅助库，这一点是进步。下一步应该让它们不再受自有工程子集约束。〔S3〕

我的具体建议是：

**没有使用 DTMAPI API 的普通库，不需要知道 DTMAPI 的 API 版本，也不需要承担 Mod 的身份与部署规则。**

库的“是否随 Mod 分发”“是私有实现还是共享契约”属于交付元数据，不应该要求把它改造成一个 Mod 工程。

而源码生成器、测试工程、资源转换工具是否进入游戏，要按用途判断。**只在开发机上执行的工具，不应该被强迫使用游戏加载 DLL 的目标框架。** 构建所用 .NET SDK 版本与项目目标运行时本来就是不同概念。([微软学习][4])

### 3. 不再维护任意的语言版本白名单

你提供的“简单 C# 10.0 库被拒绝”实验，说明当前限制至少有一部分来自工程解释器，而不是该段代码的宿主需求。

迁移后应尊重普通 `LangVersion` 设置，同时提供经过验证的默认值。

但这里也不能走到另一个极端：

**允许作者设置语言版本，不等于承诺该版本所有特性都适用于目标 Mono。** 微软明确提醒，一些语言特性依赖相应的运行时或类库支持，并不建议把 `latest` 当成稳定构建配置。DTMAPI 使用较新的语言设置时，需要明确自己的验证范围。([微软学习][5])

所以应当诊断“这项功能需要宿主没有的能力”，而不是仅因为版本字符串不是 `7.3` 或 `12.0` 就拒绝普通源码。

## 五、不能因为换了 MSBuild，就把游戏专用的复杂性一起扔掉

这一部分是迁移最容易做过头的地方。

### 1. 冻结 API/BCL 引用仍然有价值，但不要继续执行旧的构建策略

当前模板实际覆盖了 `Build`、`Rebuild`、`Restore`；冻结的 `DTMAPI.Author.props` 中还有：

```xml
<RestoreProjectStyle>None</RestoreProjectStyle>
<DisableImplicitFrameworkReferences>true</DisableImplicitFrameworkReferences>
<NoStdLib>true</NoStdLib>
```

这意味着，仅仅把 CLI 改为启动 `dotnet build`，并不能得到你期望的标准工程行为。〔S2〕

这里要区分：

**保留冻结引用的字节**，与 **继续导入历史 props 的全部行为**。

我的建议是：

旧 SDK 和旧 props 保留，用于历史工程重建；新构建集成读取需要的冻结 API/BCL 引用，使用新的配置和目标接入标准构建。**不要改写旧载荷，也不要因为旧 props 必须保持原样，就继续让它关闭新工程的正常 Restore。**

引用替换、`NoStdLib` 等是否需要，应该围绕明确的编译引用集合设计，不能把历史配置整体照搬。

### 2. NuGet 的构建资产、编译资产和运行资产必须分开

当前依赖文档仍限制某些合法的 NuGet 资产模型，比如分析器/生成器、不同字节的 `ref` 与 `lib`、较低 TFM 的运行库等。〔S4〕

标准工具链已经区分编译资产、运行资产、构建目标、分析器和本机资产。DTMAPI 应该利用解析结果，而不是再发明一套包解析方式。([微软学习][6])

特别需要做到：

**生成器和分析器用于开发，不应因为参与构建就被打进 Mod；编译用引用程序集，不应被误当成运行实现程序集；NuGet 正常选中的运行库，还要继续接受目标游戏和 DTMAPI 的交付检查。**

因此：

> **NuGet 能还原，不代表游戏一定能加载；但一个包带有构建工具，也不代表它必然不能用于开发 Mod。**

游戏已经驻留的 Newtonsoft.Json 就是很好的反例。当前文档已经区分“NuGet 还原与打包成功”和“私带版本能否与游戏版本共存”，并提供 Advanced 宿主引用路径。这个判断应该保留，不能因迁移而变成“标准构建成功就全部放行”。〔S5—S6〕

### 3. Native 编译视图和运行时契约仍应保留

你的 SDK 不只是找一个 `Assembly-CSharp.dll` 来引用。当前文档还描述了编译视图生成、宿主身份记录、实际使用成员扫描以及 Native V2 泛型表达。〔S5〕

这些是多洛可小镇特有的工作，属于 SDK 的合理职责。

但应把两种承诺分清：

**SDK 尽力证明引用与签名关系成立；作者仍要验证游戏行为是否正确。**

存在同名同签名的方法，不证明它在新版本中仍具有完全相同的行为；构建成功，也不能代替目标 Mono 的实际调用测试。Unity 对外部托管插件本身也区分编译目标与运行兼容性，并要求关注实际运行环境。

### 4. 打包必须检查“最终文件”，不能只相信构建过程中的记录

这是接入自定义生成、后处理后尤其重要的一点。

作者可能在正常编译后再加工 DLL、生成资源或调整输出。因此，打包阶段应该对最终待发布文件重新检查，生成与这些字节一致的依赖、Native 和文件清单。

**不要从 `bin` 目录里随便找一份 DLL，也不要把整个目录递归压缩当作准确打包。**

更合理的方式是：读取标准构建明确提供的输出和交付项，准备本次暂存文件，完成检查与摘要绑定，然后生成 ZIP。不要在检查完成之后再允许未受记录的修改。

这里完全可以复用现在的包清单与验证成果，无须新造另一套协议。

## 六、真正帮助作者的地方，应该集中在开发过程中的这些问题

我会优先追求以下体验，而不是继续增加构建规则。

### “我应该引用什么？”

SDK 默认准备正确 API 引用，提示选定目标、稳定性与宿主要求。Native 作者显式选择本机安装；有多个安装时不能悄悄引用错误版本。

常用接口的 XML 文档、IDE 提示和可运行示例，应当比让作者翻阅大型状态矩阵更容易获得。

### “我已经有一个普通库，能不能直接用？”

应该可以通过普通 ProjectReference 接入。

需要限制时，指出最终产物的具体问题，例如缺少运行依赖、引用了宿主无法提供的 API，而不是要求作者把整个库改写成 DTMAPI 工程。

### “构建成功了，为什么游戏里没变化？”

SDK 应当能够明确区分：

**本次构建文件、已经安装的文件、游戏当前进程实际驻留的程序集。**

你当前 session 与符号诊断已经在处理这些问题，值得继续保留。尤其不能把“磁盘更新成功”显示成“当前游戏已经加载新代码”。〔S7〕

### “出错了，我下一步该干什么？”

错误最好直接说明原因和操作，例如：

> 该依赖与游戏已经加载的程序集发生身份或内容冲突。当前包不能通过携带另一份同名库解决；请改用已支持的宿主引用路径。

而不是只给作者一个 `SDKxxx` 和“违反政策”。

同样，PDB 匹配、堆栈行号和断点调试应该分别报告。你当前文档已经诚实区分这些能力，迁移时不应改成“生成了 PDB，因此已经支持 IDE 调试”。〔S7〕

**好的作者体验通常意味着错误更具体、默认值更合适、重复操作更少，而不意味着增加更多自动控制。**

特别是当前官方 MODS 安装、官方界面启停的责任边界，应当继续保持。普通 Build 不需要偷偷安装、修改玩家启停状态或替作者启动游戏。

---

## 七、迁移必须坦率接受三个取舍

### 1. 标准构建可以执行代码，不能继续保留旧的安全表述

你的自有子集不执行任意 MSBuild 任务，这是一个真实边界。

切换后，作者的构建目标、部分 NuGet 构建资产、分析器和生成器都可能执行代码。微软甚至提醒：还原工程、构建工程，以及在 IDE 中打开工程，都应考虑工程扩展代码的可信性。([微软学习][7])

因此，新架构应该明确：

**构建可信源码，是执行作者选择的构建过程；检查陌生 Mod 包，则应当保持非执行式检查。**

Doctor 扫描 ZIP、manifest 和程序集元数据时，不应该为了“验证更完整”而调用陌生项目的 MSBuild、执行生成器或加载其程序集。当前 Doctor 的非执行式检查边界值得保留。〔S7〕

不要试图一边承诺正常的自定义构建能力，一边继续承诺“任意工程扩展永远不会执行”。

### 2. 离线、自包含可以保留，但需要实际携带标准工具链

标准 MSBuild 不意味着作者必须手工配置一大堆环境。

可以提供经过验证的本地 .NET SDK、DTMAPI 引用包和本地 NuGet 源；官方安装工具也支持非管理员、指定目录的 SDK 安装方式。([微软学习][8])

但要承认：

**便携完整 SDK 的体积与准备成本，可能比只携带 Roslyn 和运行时更高。**

离线能力也应该写清楚条件：所需工具链、引用和依赖已经具备时能够离线构建，而不是承诺未知依赖第一次出现也能无中生有地还原。

可以保留一个 SDK 版本的普通包与离线完整包；它们只是分发内容不同，**不需要对应两套编译后端**。

### 3. 确定性编译，不等于任意工程都可完全重现

你贴出的哈希实验足以支持“自有工程解释器不是确定性输出的必要条件”。

不过，切换之后也不能承诺：

> 只要有相同源码，任何机器上的任意自定义构建步骤都能产生相同 ZIP。

编译器版本、引用、资源、生成输入、路径以及分析器等都会影响输出；微软的确定性编译文档明确列出了这些输入。([微软学习][9])

建议把两个目标分开：

**日常构建**尊重作者工程；**需要严格重现的发布构建**固定工具链、依赖和必要环境，记录实际输入，并验证输出。

标准 NuGet 锁文件与 locked restore 已能承担依赖锁定的一部分工作，不需要再让作者创建一个依赖专用工程后手动复制锁文件。([微软学习][6])

同时，SDK 的引用摘要和构建记录是兼容性、完整性与排错证据，**不是这个 Mod 安全无害的证明**。

---

## 八、这次应该怎样实施，才不会又演变成长期返工

我支持你提出的：**作为一次完整改造任务实施，验收通过后切换一个正式后端。**

但是“一次完成”的完成标准，不能只写成“把 Build 改为 MSBuild”。

### 改造范围应收敛在作者构建与交付链

保留冻结 API/BCL、Native 契约、依赖检查、打包、Doctor、官方安装与现有运行验证机制；替换自有工程解释及编译组织。

不要夹带重做 GameBridge、全面修改 API、建立新插件市场或编写通用沙箱。只有现有交付契约确实无法承载必要产物时，才做有证据的最小调整。

### 迁移时要保留旧工程的有效设置，而不是恢复一切默认值

当前 Mod 模板的 checked arithmetic、nullable、语言版本、版本号来源和输出路径等，与普通新建工程不完全相同。〔S2—S3〕

迁移应把需要保留的设置明确写进新工程，而不是因为“回归标准”就悄悄改变运行语义。

与此同时，修复 `NETSTANDARD2_0` 等问题本来就可能让源码进入不同分支。应该明确报告这种变化，不能笼统声称“换了构建后端，所有源码行为完全不变”。

**旧包保持兼容，不等于同一份旧源码使用新 SDK 重新编译后必须产生旧包的相同字节。**

### 我建议至少用这些外部行为验收

| 验收方面       | 完成标准                                                         |
| ---------- | ------------------------------------------------------------ |
| **标准工程语义** | 你列出的 `.editorconfig`、框架常量和普通 C# 10.0 示例符合标准工具链行为；不再经过私有语法白名单 |
| **普通项目组合** | 普通辅助库、项目引用、资源和一个真实生成器正常工作，不需要在 DTMAPI JSON 中重复声明             |
| **构建入口**   | CLI、IDE、CI 的有效编译输入一致；Clean、Rebuild、Debug/Release 和增量构建行为清楚   |
| **引用与依赖**  | 冻结引用仍准确，宿主 DLL 不被误打包，依赖冲突仍能被识别，生成器不进入游戏包                     |
| **最终产物**   | 打包的 DLL/PDB 与本次构建对应；Native、依赖和清单绑定最终待发布字节                    |
| **作者流程**   | 未登记的新作者能完成 Strict 和 Advanced 项目，不依赖仓库内部脚本或产品 Catalog         |
| **真实游戏**   | 至少覆盖普通加载、Native 泛型调用、异常定位、停用清理与代码更新后重启                       |
| **兼容与重现**  | 旧交付包仍按原承诺工作；新后端在固定有效输入下可重复构建；不覆盖旧 SDK 历史载荷                   |

这里要特别强调：**都叫 MSBuild，也不自动证明 CLI 与 IDE 输入一致。** 工具链选择、配置、引用和扩展任务仍要实际对照，不能只比较入口名称。`global.json` 可以控制 SDK 选择，但实际生效版本仍应记录。([微软学习][4])

验证用少量有代表性的外部工程即可，不必再创建一套庞大的治理体系。关键是这些工程确实位于 DTMAPI 仓库之外，使用作者会使用的公开入口。

---

## 最终建议

我会把下一版 SDK 的设计原则写成下面这段，作为这次改造的约束：

> **DTMAPI SDK 提供游戏专用的默认配置、引用、诊断、交付和排错能力；普通 C# 工程由标准 MSBuild/NuGet/Roslyn 解释和构建。**
>
> **作者只声明一次普通工程信息。平台限制必须对应明确的运行或交付契约；维护偏好使用默认值或可配置建议，工具尚未支持的情况不得冒充游戏能力限制。**
>
> **CLI、IDE 与 CI 使用一个正式构建体系。运行时验证最终包，而不以作者是否使用某个专用编译入口代替兼容性判断。**
>
> **保留旧载荷与已有有效检查，不长期维护两套默认编译流程，不继续扩充专用 csproj 子集。**

**衡量 SDK 做得好不好，不应看它控制了多少东西，而应看：一个作者使用普通 C# 开发习惯做出你没有预想过的 Mod 时，SDK 能替他处理多少游戏特有的麻烦，又有多少地方需要他回来请求“请再支持一种写法”。**

这次迁移最值得追求的，就是让后一种请求大幅减少。
